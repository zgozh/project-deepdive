# Phase 6 源码主题写作卡

这张卡把已安装的旧教材 `references/批次讲解全文模板.md` 中由 `scripts/new_batch.py` 生成的 17 项职责，改写成 Phase 6 读者章作者可直接使用的覆盖骨架。它用于写前规划和逐文件教学，不是第二套课程目录、canonical 章节稿或自动语义评分器。

**每个 source-rich 读者主题起笔前都要用这张卡建立作者覆盖计划。** 读者目录仍按项目目的、业务问题、架构、必要工程基础、完整功能路径、机制、失败和验证组织；不要按 curriculum unit、随机类或文件批次排课。可复用旧模板与 `new_batch.py` 的骨架生成、旧批次 preflight 与 `lecture_checks.py` 的确定性检查能力；读者正文继续使用 `reader_source_blocks.py` 呈现冻结源码，不因此改走旧批次发布或门禁。

## 17 项职责映射

| 旧模板标题 | 写作者要覆盖的作用 |
| --- | --- |
| ① 在系统全景中的位置 | 说明本主题在项目整体里解决哪一段问题，以及边界在哪里。 |
| ② 业务场景与端到端闭环 | 用一个业务动作说明起点、关键交接和可见结果。 |
| ③ 文件清单与一句话职责 | 列出闭环实际经过的文件，并说清各自负责什么；它只导航，不代替深读。 |
| ④ 新概念白话解释 | 在首次依赖术语、语法或框架行为前，用初学者能懂的话解释。 |
| ⑤ 批前两个内部清单 | 写清调用了谁，以及每个核心文件准备讲哪些职责；作为作者计划，不作为读者的审计目录。 |
| ⑥ 逐件讲解（完整代码 + 逐行说明） | 每个项目源码块前交代场景、架构位置、先修概念、输入输出与真实创建/调用关系；块后紧跟覆盖该块全部真实仓库行号的专属解释表，再回放正常/失败路径、上下游、边界、取舍与实际用法。 |
| ⑦ 调用链、数据流、状态变化与边界 | 带真实行号重放同一输入经过的调用与数据变换；对象有状态时说明状态转换，并解释不变量和资源边界。 |
| ⑧ L0-L4 底层穿透卡 | L0 给源码证据，L1 讲实际机制步骤，L2 演示最小等价并列出未覆盖的生产边界，L3 解释取舍与失败，L4 仅记录有证据的故障实证。 |
| ⑨ 八股讲解（本批涉及的面试与工程常识） | 只在获得授权的独立面试/工程常识任务中展开，不把它伪装成源码事实。 |
| ⑩ 失败反例 | 选一条真实或明确标为假设的失败输入，说明失败位置、可观察后果和恢复/验证方式。 |
| ⑪ 测试视角 | 说明哪些测试能保护本主题行为；测试建议与实际执行结果分开写。 |
| ⑫ Vibecoding 视角 | 旧模板包含完整的 VibeCoding 开发训练；当前 Phase 6 初始教材不要求完成整套独立训练。 |
| ⑬ 验证证据与已知限制 | 区分源码观察、实际运行结果、未执行的验证建议和未知行为。 |
| ⑭ 复习问答 | 给出可由本章内容独立作答的问题和展示推理的完整答案。 |
| ⑮ 前置知识 / 后续依赖 / 未覆盖项 / 下一批入口 | 标出先学什么、本章产出被哪里使用、哪些目标仍未讲完和准确的后续入口。 |
| ⑯ 教材质量自检 | 检查初学者能否依照输入和源码解释结果；这是作者复核提醒，不是自动 PASS。 |
| 索引节（旧骨架第 17 项） | 提供有助于学习和定位的链接；索引不能替代正文中的就地路径、行号和解释。 |

这 17 项是**完整的作者覆盖骨架**，不是读者必须看到的 17 个标题、17 份 Markdown、固定总章数或机械配额。把适用职责写进连贯的读者正文；确实不属于当前主题的职责，简要说明原因，不用空标题凑数。当前 Phase 6 范围不包括独立八股/面试任务或完整 VibeCoding 训练，⑨与完整⑫标为 `not_requested`，不宣称 17 项全通过；主题涉及的⑧机制讲解仍然属于当前写作。旧 v2.31 门禁仍约束旧批次路径；不能给新读者稿盖 `legacyPASS`，也不能通过修改这张卡削弱旧判据。

## 每个项目源码块的前、中、后讲解与完整行号表

这是对既有逐件讲解职责的落实，不新增课程范围或固定标题。它适用于正文里**每一个项目源码块**，包括总览中的短引用，不只核心深读块。源码块前沿用上面的业务、先修、构造与上下游骨架，说清为什么要看它、它在架构哪里、谁在什么条件下创建/调用它，以及这段代码收到和交出的具体值；需要的图按主要主题讲架构和调用/时序关系并配文字解释，不为每个 getter 单独画图。

正式读者稿的 `reader_source_blocks.py` 会按源码路径与起止行号自动为每块生成唯一的 `源码位置` caption；使用 helper 时保留该 caption，不要重复手写。直接读源码且某块不适用 helper 时，作者在块前写明真实仓库相对路径和原始起止行号，并从同一份冻结源码原始字节核定行号。两种 caption 都只用于定位，不是来源回执，也不代表来源或教学复核 PASS。

源码块保持 helper 呈现的原始字节与安全注释规则。每个块闭合后，除空行或一个简短小标题外，紧跟它自己的 Markdown 行号表；表首列为 `源码行`，表中使用 caption 对应的**仓库绝对行号**，不是 Markdown 行号或块内相对号。对 caption 的闭区间逐行覆盖，不能漏行或越界。空行、注释、license、imports 和闭合括号可以与相邻的完整职责段合并解释，不要求每个物理行单占一表行；合并时仍要说明这些行在该段中的作用。表格其他列按源码定制，让读者能查到关键值、分支、赋值/调用、副作用、返回或异常及其去向；配置表应使用字段、有效值、读取/继承位置、生效结果等能解释配置的列。泛泛的“处理数据”不能代替这些可定位解释。

叙述使用自然中文，先讲清谁在什么场景做什么、得到什么，再引入术语；用有意义的业务名称，避免 A/B/C 或索引占位增加读者转换负担。教学人物和流程须标明为假设，不强行造故事或凑配额。源码行号列固定，其余列名和数量按代码语义决定（三、四、五列都可以），不复制无关通用列或为版式硬拆；例如配置可讲字段/取值/效果，分支可讲条件/变化/退出，函数可讲输入/返回/副作用，这些只是选择参考，不是配额。

表格单元格中的字面管道符必须转义，包括行内代码中的 `||` 和联合类型；保留已有的 `\|`，不要重复转义。编辑后检查表头和每行的列数一致，内容里的管道符没有变成额外列。

源码注释只作线索，不能机械拼成职责或让每行重复整块结论；表格按有意义的职责段解释实际字段/变量变化、guard、副作用、返回/异常及去向。表格也不能替代源码前的场景、先修、架构与输入输出，或源码后的同输入正常/失败推演、真实上下游用法和必要机制/取舍教学。

作者每次都从不可变冻结输入与独立作者部件重建成稿，不在旧渲染稿上追加。行号分组用确定性编号的原始冻结源码核对；保留已有正确的细粒度解释，只补缺口，数字覆盖不证明行义对应正确。

先按确定性编号冻结源码中的真实条件、赋值、调用、返回和捕获边界划分职责段，再写解释；不要先画行号区间猜职责。长方法要保留关键分支与值变化，不能用一行概述遮住它们。图、正常路径、源码表和答案须核对同一静态调用顺序及字段去向；复制/可变性、配置特殊值（例如非正数表示不限）、异常传播等结论须核对实际执行语句，注释、记录类型或接口名称不保证实际行为。独立语义抽查不能由行号覆盖 PASS 代替；确认错义后，还要检查本章同类表述是否存在相同错误，再作最小修复。批量替换应先选唯一上下文并核对预期匹配数，禁止默认替换首个或全部同形表述。

表格只是源码中的定位与因果说明，不能代替其前后的教学。表后用同一输入逐步回放正常分支和有依据的失败分支，交代每次关键变量变化、真实返回/捕获状态、日志行为、上游如何检查结果和证据支持的下一跳；机制说明只讲当前代码实际依赖的语言/框架/HTTP/MQ/事务/持久化知识。静态可推导的规则可以结合官方资料和明确标注的教学示例讲透，不得因为没有运行项目而省略必要机制，也不得把推论说成实测；项目内部链仍需源码/运行证据。扩展步骤只适用于源码证实存在的扩展点。若 caption、源码块或表格不能可靠对应，标为未覆盖并修正，不猜测绑定。

相邻片段可以共用已讲清的先修背景和整章输入推演，但每个块仍要就地说明自身输入、职责和交接；不能只写“见前文”。总览保持概览，不为覆盖数字扩大源码范围或把深读内容塞入总览。

假设分支的表格示意（这些行号不是仓库事实）：源码范围 40–45 中，40 为 `if (...) {`，41 为早退 `return`，42 是空行，43 是分支闭括号，44 为正常 `return`，45 为方法闭括号。对应表可用两段覆盖：`40–43` 解释条件、早退和包含空行/闭括号的分支边界，`44–45` 解释正常返回与方法结束；区间合起来必须无遗漏、无越界。

假设配置表示例的列随配置机制定制：

| 源码行 | 字段 | 有效值/默认值 | 读取或继承位置 | 生效结果 |
| --- | --- | --- | --- | --- |
| 7–8 | `service.port`、`service.timeout` | `9090`、`2s` | 环境变量可覆盖文件默认值 | 说明最终连接目标与等待边界 |

`scripts/reader_source_explanation_coverage.py` 只按严格 source manifest 绑定的项目源码块、`reader_source_blocks.py` caption、围栏和相邻表统计行号覆盖；报告 `COVERED`/`INCOMPLETE` 以及数字缺漏，不做语义评估或来源认证。默认仅检查绑定到 `lesson.md` 的块；若清单还含 `answers.md` 块，会报告排除数并使整体保持 `INCOMPLETE`。最终正文已嵌入或追加完整答案时，使用 `--assembled-chapter` 同时核对两类块。教学示例也要逐段解释，但用“示例行”或逐步演算定位，不写成仓库行号，也不计入源码覆盖。不能可靠解析的范围保持 `INCOMPLETE`，由作者补齐后交独立审查。

## 每个核心文件可直接填写的小节骨架

核心文件可按整个文件讲，也可按连续、完整的职责段拆讲。源码范围按完整符号与职责边界选择：已有 source-pack excerpt 只作导航，不是强制裁剪边界；优先复用已有符号起止元数据，元数据不足时窄读同一冻结文件，确认范围从完整声明延伸到方法、构造器或类的实际结尾。不得截在 `return`、链式调用或闭合大括号之前。若解释结果依赖私有 helper/visitor，本章须呈现并解释必要的完整实现；否则把依赖它的学习结果标为未达成。小文件整件讲，长文件按连续完整职责段拆讲。每个核心文件分别填一份；不要只挑几个摘录就声称整类、整文件已教完。配置文件要解释本主题涉及的所有有效配置字段；尚未覆盖的方法、字段或职责要留在未覆盖项中。

1. **业务问题与输入/输出**：这个文件为什么参与本次业务动作？本段拿什么输入，交出什么结果？
2. **先修概念**：首次依赖的名词、语法、接口、框架职责是什么？先给直觉和小例子。
3. **构造、生命周期与手法**：谁创建它、何时调用、数据如何进入；回调、事务、异步或资源由谁持有和结束？在机制涉及实际用法时，指出有证据的调用处/调用方，并用一个具体输入展示最小教学用法如何交入数据、产出结果或进入失败分支。项目中实际创建、调用、状态和外部效果须有源码或运行证据；通用语言/框架机制可用官方资料及明确标注的教学示例讲清，不因未执行项目就跳过必要先修或只重复 API 名，也不据此补造项目内部链。对不承载此类机制的简单声明或 getter，不虚构调用故事。
4. **源码槽与安全注释**：在随文 source-plan 中记录源码路径、行号、语言和逐行解释计划；用 helper 支持的整行槽位填源码。`reader_source_blocks.py` 会给出定位 caption，正文不得再手写一份重复 caption；源码字节保持原样。XML/JSON 代码块的 source manifest `annotations` 必须为空对象，逐行解释放在代码围栏外、带源码行号的表格中；其他语言也只在 helper 明确支持的安全位置写注释。声明展示完整核心符号时，从冻结符号提取结果记录其完整范围，并用 `required_symbols` 检查源码块范围并集确实覆盖它；局部旁证无需申报完整符号。例：`from reader_source_blocks import RequiredSourceSymbol`，再传 `RequiredSourceSymbol(path="src/example.py", name="build_request", start_line=7, end_line=9)`。整章标准组装时，按稿件分别交给 `compose_reader_manuscript(..., required_symbols={"lesson.md": (...), "answers.md": (...)})`；每份稿件只用自己的 source-plan 范围覆盖已声明符号，不能跨稿件凑范围。此检查只证明范围覆盖，不证明逐行职责或讲解语义。
5. **源码行号表与逐段因果**：每个展示的项目源码块都必须在块后附一个专属表，按本节第一部分完整覆盖 caption 的仓库行号范围、不能漏行越界，并依源码职责定制列；表格不是可选项。代码前仍须交代场景、先修、输入输出与位置，代码内/表中说明关键变量、条件、赋值/调用/副作用、返回或异常及其去向，代码后仍须演算和机制讲解。对关键正常/失败回程，逐层区分抛出的异常、实际捕获后的返回状态、日志行为和上游如何检查返回值；不能从被调用方抛异常推定 HTTP、CLI 或 MQ 外层一定失败。表格定位不能替代这些教学文字。
6. **同一输入的两条推演**：沿同一个输入分别走正常分支和一条有根据的失败分支，逐步说明结果、错误处理和后续状态；运行时未观察到的外部效果标为未知。
7. **真实上下游与怎么用**：说明有证据支持的实际调用方/调用点如何把值交来、谁使用输出，以及跨文件/跨线程/跨服务的交接点；给一个与本段职责相关的具体输入输出或最小调用演算。不要从文件名或方法名猜链路；职责为纯声明、且本章没有证据内调用处时，明确该边界而不伪造用法。
8. **机制、等价实现、取舍与边界**：解释真正参与的机制、为什么采用该做法，以及副作用、并发或资源边界。机制适用时，L2 要用最小教学实现复现关键操作，并明确它省略的生产边界；L3 要比较实际可选做法、成本与相关失败面。通用机制可用官方资料和明确标注的最小示例解释，静态规则推导项目结果时写明条件和推理且不称为实测，外部效果仍按证据范围说明；手写等价必须实现所声称的关键动作。简单声明/getter 只解释其适用机制，不强行添加等价实现或方案比较。
9. **扩展点（仅在真实存在时）**：先指出源码证实的扩展点，再按实际调用路径说明接入步骤；没有证据就说明本范围未确认可扩展，不虚构接口。

输入、冻结源码和来源元数据已备齐时，先写连贯的章节正文和完整答案，不要把广泛找资料本身当作教学进度。随着正文安排在 source-plan 中标记槽位；正文稳定后，再集中使用 helper 呈现源码块并收集它返回的字节级来源证明，依据同一份 source-plan 一次整理 `sources.json` 与旁路 provenance。哈希由源码呈现和章节生命周期按实际字节计算，不手填猜测；清单 shape 检查只证明形状，不证明来源或教学。后续只复用未变化的源码证明，改了源码范围再重呈现受影响的块。读取冻结源码时，始终从原始 bytes 做严格 UTF-8 解码；在 Windows 上用 Python 把中文送入工具输出时，运行 `python -X utf8` 或显式设置 UTF-8 stdout。捕获结果乱码只说明输出或捕获编码链可能不一致，不能据此判定源文件编码损坏或改写冻结源码。
另需区分 stdin 输入：Windows PowerShell 通过管道传送含中文字面量的 Python 源码时，可能在到达 Python 前已损坏，`python -X utf8` 不会恢复受损的 stdin；可将程序按 literal UTF-8 写入 `.py` 后运行 `python -X utf8 文件`，或用纯 ASCII 程序加 Unicode 转义做诊断。

清单中的 `critical` 要绑定本次获准且必需的学习结果：未实测本身不自动构成关键阻断，缺少必需源码或因果解释仍应阻断。不得为绕过既有门禁自行降级；若把未授权的运行目标误列为本章必需目标，保留原稿并记录范围冲突，由 Principal 独立确认获准目标后再修正分类。

写 Markdown 时，用 `tools.apply_patch` 配合普通双引号 JavaScript 字符串；转义字符串中的换行和双引号，保留内容需要的 Markdown 反引号，不用 JavaScript 模板反引号包整段 Markdown，也不删除正文反引号来迎合 wrapper。
