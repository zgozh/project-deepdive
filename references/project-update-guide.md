# 项目修订与选择性更新指南

本指南描述一种自然语言驱动的协作流程：AI读取目标项目当前可访问的版本库、已保存索引/图/证据/教材，以及作者的中断记录，再帮助人判断哪些旧结论仍成立、哪些章节确实受影响。现有工具能提供文件清单、部分符号关系、图和覆盖检查；当前没有确认一个能自动把任意Git diff准确映射到全部事实、教材和审计结论的工具。因此影响匹配由AI协助、作者核实，不能称为确定性自动映射。

## 先还原更新两端

开始时确定已发布或已接受教材对应的基线revision A，以及当前要说明的revision B。记录仓库根目录、所用快照是已提交树还是工作区字节、读取时间、作者已有修改和本次授权范围。所有比较必须说清A与B的身份，不能只写一个含义不明的 revision。

目标在Git仓库时，先读取 `git rev-parse HEAD`、`git status --short` 和当前分支信息。工作区可能同时有提交、暂存区、未暂存修改、未跟踪文件；它们彼此不同，逐类列入本次比较。`git diff` 不含未跟踪文件，新增文件要从状态和文件清单中补入。

提交树A到B的文件变化可使用Git现有差异输出，例如 `git diff --name-status --find-renames A B`，再对有影响的路径查看逐行diff。工作区差异则分别查看未暂存和暂存变更，并明确B是当前提交、暂存树还是含工作区修改的快照。重命名记录同时保留旧路径、新路径和被确认迁移的符号。

没有Git或无法读取指定revision时，比较冻结基线和当前文件字节/文件清单；写清比较方法和缺口。不要假装存在一个兼容所有项目的revision扫描CLI。

## 从路径追到真正受影响的教学结论

按文件路径、状态和hunk整理变更：修改、新增、删除、确认重命名、未跟踪、无法分类。对配置、依赖清单、构建脚本、路由、schema、测试和文档分别说明它们可能改变的事实边界；纯文本差异本身不能证明运行行为改变或未改变。

先用当前有效的项目索引找到真实文件和已识别符号，再对照知识图/调用图/工作流图，查相邻调用者、被调用者、接口实现、数据结构和跨层边。删除、重命名或新文件特别容易让旧依赖边失效；需要确认旧边是否仍存在、应迁移到哪里或已无法证实。

对每一项拟保留、修改或撤销的项目事实，记录真实仓库path、symbol或源码范围、支持该结论的实际引用位置，以及所比较的revision。再检查这项事实出现在哪些知识图主题、claim/证据条目、核心教学单元和质量结论中。作者的最终教学正文引用读者能打开的实际path/symbol/行号；artifact内部ID只用于工具间连接，不拿来代替来源位置。

如果现有图或artifact没有提供能核对的关系，AI可以从diff和源码推理候选影响，但这是待核实的映射，不是工具已证明的边。让AI列出推理所用的文件、符号、调用者和主题，并指出缺失的一跳；无法补证就标 UNKNOWN，不能凭文件名猜章节。

下列变化需要额外检查相邻事实：公共接口、schema或序列化格式变化；构建与依赖变化；服务端返回和前端消费变化；共享状态、异步边界、权限、错误处理或事务行为变化。只扩展到真实依赖链和受影响消费者，不因revision变化自动重审每个教材段。

## 判断旧材料是否仍可复用

对未改文件上的旧来源，核对它在B仍存在、内容摘要或被引用范围仍相同，且没有变化的调用者、配置或依赖关系改变其解释。保留其原始证据revision与现次核对依据；不要只把artifact顶部的revision改成B，就把旧事实包装成新验证。

对有改动的文件，按源码符号和diff hunk核对旧引用。若内容只是移动，更新真实路径/行号并重新确认上下游；若关键语句、条件、返回、异常或依赖变化，则重写相关事实和解释。上游定义或配置变化即使源码行未动，也可能使下游说明失效。

对删除的文件，撤销或重定位所有只由它支持的事实和章节引用。对新增文件，先确认它是否进入真实构建、注册或调用链；未跟踪不等于已生效。重命名需核对对象身份，不能因Git报告R就直接继承所有旧关系。

只有在来源、依赖边、revision语义和本章论证仍适用时才复用旧内容。把状态区分为：已核实仍有效、受影响待重写、来源迁移待核、证据丢失/未知。此为作者解释，不要求新增一套JSON状态schema。

## 只更新受影响范围

将每个受影响文件/符号连到它支持的事实、主题和教材位置，形成一张可由作者复核的影响表。表中分别记录差异位置、证据、关系依据、影响判断、待采取动作和检查方式。没有匹配关系的差异留在未映射项，直到人工查清。

只改受影响事实和章节；其余材料保留原字节或仅在现有发布流程要求时重新组装。重建一个完整bundle不等于逐章重写，若真正的编译器只接受整体组装，也应尽量复用已核实的既有章节内容。

更新正文时先重新定位本章实际展示的源码和命令。重新解释受影响的关键值、分支、返回、异常和调用交接；为本章选择一个具体输入重放正常路径和相关失败路径。前后端项目还要查真实UI、客户端、API、服务、持久化和界面回写链；不存在的层标明边界。

教学正文使用可读来源位置，不插入内部evidence编号充当解释。通用语言/框架机制按实际版本查官方文档或标作通用解释；项目运行事实依来源证据和实际观察区分。没实际运行的命令写NOT_RUN。

## 选择检查并保存可恢复进度

检查只覆盖更新改动影响的路径、符号、artifact关系和教材结论。命令从目标项目真实清单、测试配置和当前允许的环境中选择，保存实际cwd、完整命令、revision、退出码和结果位置；不安装缺失依赖，不把静态检查看作运行验证。

当前可用工具可按需要组合：从Skill根目录运行[仓库扫描器](../scripts/scan_repository.py)读取实际Git仓库并输出 `project-index.json` 与 `coverage.json`；其 `--root`、`--out`、`--snapshot {worktree,git-tree}` 参数以真实CLI为准。只在文件清单或快照需要更新时使用，不把它描述为diff影响映射器。

已有 `validate_coverage.py` 可将真实 `project-index.json`、`coverage.json` 和根目录作覆盖一致性检查。已有 `build_phase4_graph.py` 需要通过校验的Phase 3 run目录；`build_prerequisite_graph.py` 需要真实Phase 4候选与认证package。缺少这些前置artifact时，不运行、不合成、不绕开校验。

这些工具只证明它们各自定义的结构或覆盖关系，不证明某段教材解释正确、每个影响边完整、程序行为或教学有效。若重建图需要的工具前提不满足，沿已存在来源手动追踪并明示部分覆盖；不能宣称工具已完成重算。没有经核对的更新CLI时，就按现有作者流程局部修订并记录实际diff。

被中断后，先读取磁盘上已有的基线artifact、最后一次diff、已更新章节、审核/命令记录和作者当前会话交接，再读目标项目当前revision与工作区状态。用实际现状确认哪些步骤完成、哪些未完成；继续最早一个未完成动作，不重复有效验证，也不声称存在后台任务。

保存恢复信息到当前任务已有的handoff、checkpoint或作者记录：基线与当前revision、未完成差异、最后完成步骤、未做的检查、真实输出位置和待解决UNKNOWN。不要为恢复强制新建JSON schema或只依赖聊天上下文。

更新只有在全部差异都有明确处理状态、引用与revision仍诚实、受影响章节已修订和复核、必要的定向检查有真实结果或明确NOT_RUN时才可作为候选完成。映射不清、来源丢失或执行受阻时报告PARTIAL/待补证。AC-18要求识别受影响实体/章节且无需重生不受影响内容；格式校验不能替代这一判断。
