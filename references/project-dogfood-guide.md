# 双项目 Dogfood 指南

Dogfood 是在真实目标仓库上检查Project DeepDive核心流程是否能产出有用且有证据的结果。按本 Skill 随附的[产品质量门镜像](product-quality-gates.md)和[产品验收标准镜像](product-acceptance-criteria.md)核对 G21、AC-19–24。验收至少覆盖一个非平凡Python/Agent项目和一个非平凡Java企业项目；它不证明任意语言或所有项目都受支持，也不等于把两套教材全部重写。

## 选择安全且有代表性的输入

从已经存在、可读取且获得授权的仓库中各选一个项目。项目应足以暴露真实模块、业务工作流、框架接入和测试边界；一个几文件的玩具仓库或纯合成JSON不代替Python/Agent与Java企业输入。

优先选择至少一个包含真实前端或UI的项目。若目标存在前端，前端是核心证据链的一部分；挑一个实际用户功能，追踪UI操作、组件状态、API客户端、后端入口、服务/数据访问、持久化结果和界面更新。某一层不存在或材料不足时如实标出，AC-21未覆盖就保持未通过或部分完成。

选项目时记录真实根目录、revision、当前提交和工作区状态、所用快照、授权读取/运行/写入范围、可用环境与任何已有测试失败。不要覆盖用户已有文件。输出放到目标仓库之外且实际获准的目录；没有隔离输出权限时先停在只读盘点。

先复用本机已有运行环境和依赖。若确有缺失依赖，说明来源、安装动作和影响；只有用户已有授权明确覆盖该安装时才可在该范围内执行，并记录真实安装结果，不重复询问已给出的授权。没有安装授权时不自动安装，记录依赖名称、命令来源和NOT_RUN；静态或人工证据与运行结果分开。

## 为两个项目分别产出证据

先逐项目冻结输入身份，再生成或复用该项目revision对应的仓库索引、技术栈profile、知识/调用关系、前置图、源码讲解和质量记录。一个项目的证据不能填补另一个项目的缺项。

仓库扫描器的实际入口是[scan_repository.py](../scripts/scan_repository.py)。在 Skill 根目录（包含 scripts 与 schemas 的 project-deepdive 目录）打开终端作为 cwd，先读该脚本的 --help；--root 指向目标仓库，--out 指向目标 root 之外且用户授权的输出目录。输出目录可以在 Skill 工作区之外，不把它限制到 Skill 安装目录；这样也避免扫描器把自己的报告当作目标仓库文件。CLI 会将 project-index.json 和 coverage.json 写到该目录；它自身还拒绝覆盖 tracked repository file 或 overrides 输入。把本段的真实绝对路径填入教材，不要把指南参数说明当作已经扫描过目标。

命令模板为：python scripts/scan_repository.py --root 〔目标仓库绝对路径〕 --out 〔目标root之外且已授权的目录〕。作者必须先填入真实路径；不要把方括号占位符直接交给终端。

当用户已授权一个目标 root 之外的报告目录，直接复用该授权；没有获准输出位置时停在只读盘点，不在目标仓库内临时创建输出。

[validate_coverage.py](../scripts/validate_coverage.py)可根据真实project-index、coverage和root核对目录覆盖，`--require-complete`会在仍有跟踪文件UNKNOWN时失败。它不审核教材内容、源码语义或目标程序是否成功运行。

[build_phase4_graph.py](../scripts/build_phase4_graph.py)依赖已验证的Phase 3 run以及匹配root和新输出目录；[build_prerequisite_graph.py](../scripts/build_prerequisite_graph.py)依赖真实Phase 4候选和认证package。只在这些前置artifact存在且属于同一目标快照时运行；CLI缺少输出或校验失败就停止并保留错误状态。

现有入口的命令行参数和前置条件可以从Skill根目录对应脚本的 `--help` 读取。本指南没有确认一个通用quality-report构建命令；沿目标项目实际存在的DeepDive流程读取其真实报告。没有可用报告时记录缺失并保留PARTIAL/NOT_RUN，不捏造质量报告CLI或JSON schema。

为每个目标准备一份人工可读证据矩阵，至少包括：验收项、目标项目与revision、真实产物路径、关键源码path/symbol/行号、实测命令和cwd/exit、人工教学审核范围、未覆盖项与状态。矩阵是本次核验记录，不是要求注册新的Artifact类型。

## Python/Agent与Java企业项目的等价能力

Python项目证明仓库文件分类、真实语言/依赖检测、至少一条核心workflow、完整核心源码教学、初学者前置、可追溯证据、真实扩展或VibeCoding练习、质量报告。

Java项目必须展示等价的学习结果，但沿其真实包结构、Spring或其他实际框架职责、模块边界、接口和配置取证；不要要求使用Python项目的装饰器、Agent Registry或相同图边表示。相同业务概念可以共享教学格式，项目事实和源证据仍分别核实。

两个项目都要检查tracked file分类是否有无法解释的UNKNOWN；分类原因要能由真实路径和仓库证据支持。索引、stack profile、知识图、前置图和源码说明必须都绑定各自当前revision或有明确的旧版本影响说明。

至少选一条完整业务工作流，让初学者从触发情景开始，经过入口、主要符号、数据变化、分支、返回/异常和调用者下一步，最后理解真实结果。若有异步续接，要追到实际回调/任务交接和错误观察点；静态分析看不到的动态行为保持未知。

每个用作dogfood证据的源码主题都应有来源定位与完整核心职责解释，业务场景和先修概念在源码前，关键行解释和适配行号表随源码，正常及失败的具体输入推演在源码后。不要只拿索引、图、hash、行号覆盖或artifact合法性代替语义与初学者理解审核。

扩展或VibeCoding练习必须锚定该项目真实工作流与扩展接缝，说明当前行为、真实影响文件/符号、调用链、风险和实际测试。仅生成一个提示词或静态lab结构，不等于已实现、已验证或已通过G15。

## 用十个核心单元做初学者抽样

AC-24要求两个dogfood项目合计抽查至少10个核心学习单元。按两项目实际课程分布选样，不必各自生成一本书，也不必固定五比五。先搜寻已冻结且revision和源码范围仍有效的现有材料；能够复用时原样引用，只有被本次变化影响的部分才做最小修订。

逐篇阅读入选单元的完整正文、每个练习和完整答案。独立检查关键术语是否先解释、先修是否先于依赖概念、例子是否来自对应项目、讲解是否沿直觉到源码机制、命令是否在出现处说明。用一组具体输入重放代表正常和失败路径，核对关键分支、返回、跨文件/异步交接和答案是否一致。

每项审核记录教材确切版本或SHA-256、真实项目revision、审核范围、未覆盖内容、学习缺口与未知行为。未看过完整章或答案、只核了源码引用/格式/hash，不能标为教学通过。

如发现术语或因果解释错误，修订完整受影响章节并对最终版本重新审核；不要为补齐十篇样本而重写其它教材。若当前只有六个有效单元，就报告6/10和具体缺口，AC-24保持PARTIAL。

## 依据验收条件记录结果

对AC-19逐项记录Python/Agent项目的文件清单、技术栈、核心workflow、源码深读、先修说明、证据、扩展/VibeCoding lab和真实quality report。任何缺项分别标为PARTIAL、NOT_RUN或FAIL，并说明来源。

对AC-20在Java企业项目上展示同等能力；相同的格式或工具输出不证明其Java框架语义已得到解释。

对AC-21只在至少一个目标确有前端时核对UI到backend到结果的全链路。接口mock仅能说明mock边界，不能说持久化或后端运行成功。

对AC-24记录十个核心单元分布和每篇的独立阅读结果、源revision/hash、审查范围与剩余学习缺口。PASS需要实际完成规定抽样，不用全书重写。

G21至少要求两个真实目标、全仓文件分类、初学者先修、源码/调用链教学、证据标签、VibeCoding lab和quality report。质量报告只能来自当前可用的真实流程；缺报告就不能宣称G21通过。

最终交付包含两个项目各自revision身份、证据矩阵、核心文件/符号定位、检查日志、十单元教学审核记录、所有PARTIAL/NOT_RUN/UNKNOWN、恢复所需路径和负责人。仅满足结构或工具exit 0不能取代真实事实及教学审查。

本指南讲的是如何安排dogfood。具体项目还需独立证明自己的代码、框架、测试和运行条件；一次Python和Java样本不能推出对所有仓库的普遍支持。
