# Phase 10：DEEP 模式运行观测指南

本指南指导 Project DeepDive Skill 在 DEEP 模式下对目标项目作少量、有界的真实运行观测。它使用当前宿主提供的终端/执行工具和已有项目脚本，不增加 runtime analyzer CLI、SDK、追踪 schema 或状态机。

FAST 只做静态分析，不自行启动目标项目。DEEP 也不是自动运行许可：用户在本任务中明确授权的命令和范围可直接执行；已有授权不重复询问。没有授权、宿主拒绝或命令有未澄清的副作用时，保留 NOT_RUN/限制，不换 shell 或其他入口绕过限制。

先用白话介绍本章用语：cwd 是终端当前所在的文件夹；环境变量是程序启动时可读取的一项配置；session ID/PID 是宿主或操作系统给正在运行任务的编号；stdout 是普通输出，stderr 是错误输出。运行器（runner）是项目用来启动程序或检查的实际工具，需从目标仓库确认。

教程作者必须把本目标项目的真实命令、目录和预期结果填进学习步骤。概念先用白话解释；每一步说明读者在哪个编辑器/终端、为何操作、真实文件在哪里、参数代表什么、是否创建文件、如何判断继续或失败。以下流程是作者方法，不是可以直接复制到任意仓库的命令清单。

## 1. 从项目实际资料发现运行方式

1. 打开目标仓库的实际根目录，在编辑器阅读已有 README、开发说明、CI workflow、测试脚本与包管理配置。先解释依赖、环境变量、端口、数据库和服务分别是什么，再指出它们在当前项目里由哪些真实文件声明。
2. 只把文档明确写出的启动、测试或请求方式当作“文档声明”。文档是待核实输入：跟进它引用的脚本，确认当前 revision 仍有对应文件、入口和参数。没有命令文档时，不从框架名称猜启动方式。
3. 在准备执行前阅读命令本身及它调用的脚本，确认当前工作目录（cwd）、读取/写入路径、网络访问、数据库/队列副作用、凭据来源、服务端口与清理行为。可能删除、迁移、发布、访问真实用户数据或触及生产环境的命令，排除在本次观测之外。
4. 选择一个代表性正常输入；若能安全、低成本地观察失败分支，再选一个合成的空值/无效输入。说明为什么这两种输入代表本次范围，不把一次检查外推成全应用正确。
5. 向学习者展示已核实的命令、准确 cwd、参数含义、预期观察和保护范围。复制到 AI 的提示必须含上述实际材料、授权范围和不得触及的数据；AI 先解释执行计划，由人核对后在授权内继续。

若目标项目有前端且本次范围涉及用户功能，优先挑选能观察 UI 输入、组件状态、API client、后端入口、服务/持久化结果、响应和 UI 更新的一条真实路径；每一段用其实际页面、请求或日志核实。浏览器或服务不可用时标出未观察的段，不从后端测试推断 UI 已更新。

具体材料缺失时，只把它记为待确认；不要求读者寻找虚构的 “runtime analyzer” 或新建记录系统。不同语言与框架使用目标实际安装的 runner 和已记录环境，不假设固定操作系统、Java/Python 或预装依赖。

## 2. 在授权边界内执行并保留原结果

1. 在实际目标仓库的终端中，先核对屏幕显示的 cwd、当前 revision 与状态，再按核准的参数运行那一条真实命令。命令若通过 shell 有组合、重定向或脚本调用，先解释各部分会访问或修改什么。
2. 通过宿主实际提供的命令工具运行；记录完整命令、cwd、开始时间、超时设置、环境变量名称（不写值）、目标 revision、输入和预期观察。成功退出后，保留原始 exit code、stdout/stderr、实际输出文件路径和相关日志位置。
3. 命令若返回 session ID 或仍在运行，保存该 session 并继续轮询同一个 session，直到观察完成或达到已说明的停止条件。不得丢弃仍在运行的会话后另报 exit code 0。若命令启动服务而预期持续运行，记录实际 PID/session 与存活状态；只停止本次启动且能精确识别的进程，不结束不属于本任务的服务。
4. 输入使用合成值或公开测试数据。日志含 token、密码、个人信息或连接串时，只记录已脱敏的摘要和受控日志路径；不把秘密贴入 prompt、质量报告或交付附件。保留真实失败原因和返回码，不为获得漂亮报告覆盖失败。
5. 不反复重跑一个无新信息的失败命令。确认了代码/配置/依赖/环境变化，或为区分一个有依据的诊断假设时，才做一次最小重试；记录每次变化与真实结果。

如果命令尚未启动且因权限、依赖、端口、缺失服务或不安全副作用无法继续，记录 NOT_RUN 与原因。若命令已实际执行但只观察到部分路径或在准备阶段失败，记录 PARTIAL，并保留执行到哪一步。预期行为的测试实际失败时如实记录失败；不要用模型猜测覆盖终端输出。

时间有限时优先完成一条有代表性的路径和必要的一条失败路径。一次通过的测试只证明该次检查确实覆盖的条件；想扩大结论前，先检查测试输入、断言和实际执行记录能否支撑它。

退出码为 0 只是命令按自己的约定正常结束；还要比对实际断言、响应或界面结果是否符合预期。依赖缺失导致行为没有执行时，报告环境限制；测试已经执行且发现目标行为错误时，记录真实失败并交 Phase 9 判断影响。

## 3. 用现有证据契约写观察记录

本仓库现有 evidence v1 schema 的一条 E3 证据包含 id、level、kind、summary、confidence、locator。运行观察用 level E3、kind runtime；locator 可放 path、command、observation。schema 没有 cwd、session、exit_code 或 environment 专用字段，所以不要增加字段。

在目标项目本次审计输出目录写简洁的 runtime-record.md，记录 revision/snapshot、命令、cwd、环境变量名、timeout、时间、session/PID（有才写）、退出/停止状态、输入、预期和实际观察、脱敏输出/日志位置、失败与限制。不要为了每个命令另建新 schema。evidence item 的 locator.path 指向该记录，locator.command 与 locator.observation 概括可复核的实际行为。

记录表可使用下列栏目；它是人读 Markdown 记录，不是新增机器 schema：

| 记录项 | 填写的实际内容 |
| --- | --- |
| 快照与命令来源 | revision、git-tree/worktree、README/CI/脚本的真实路径 |
| 授权与范围 | 获准命令、预期影响、排除的数据或服务 |
| 执行位置 | cwd、运行器、非秘密环境变量名称、timeout |
| 输入与观察 | 合成输入、预期输出、实际返回/页面/响应 |
| 进程与结果 | 开始/结束时间、session/PID、真实 exit code 或停止状态 |
| 输出与限制 | 脱敏日志路径、缺失链路、失败原因和未运行事项 |

静态来源仍用 E1/E2；只有真实执行并观察到的事实用 E3。某个测试命令成功只证明该次命令、该环境与覆盖到的检查通过；它不能单独证明服务启动、请求到达 provider、数据库写入、UI 更新或完整 UI→API→存储链。调用路径只有被实际输出/trace 观察到的部分才写为 E3，其余仍需源码证据或标成未知/推断。

记录 G19 时依据 Skill 随附的[产品质量门镜像](product-quality-gates.md)及[产品验收标准镜像](product-acceptance-criteria.md)，并引用真实 E3 ID；没有 E3 就用空 evidence_ids，并写实际原因。输出 quality-report.json 时仍遵守 [Phase 9 审计指南](project-quality-audit-guide.md) 和现有 [quality-report v1 schema](../schemas/v1/quality-report.schema.json)。不要把“运行建议”“模拟结果”或静态图表放进观察字段冒充执行。

安装后的 Skill 使用自身携带的质量门与验收标准镜像，不依赖目标项目根目录有这些文件。维护 Project DeepDive 仓库时，根文档是规范来源；对应镜像应同步更新并逐项核对。

## 4. 核对结果并教会读者恢复

执行完成后，先让读者对照原命令、输入、exit code 与日志，确认运行环境和预期一致。再用实际 source graph/源码证据比对已观察路径；日志未显示的中间步骤保持未知。完整链路缺一段就标出缺失边界，不为了故事连线。

给 AI 的复核提示附上真实命令记录和相应源码/graph 片段，要求它逐项区分 E1/E2 静态声明、E3 实测和 E6 推论。人打开原输出核实一次关键返回值；若 AI 把建议写成已观察、把局部测试成功说成全链成功，要求它修订该句、保留缺失范围并重审受影响 gate。

失败恢复要依实际原因：找错工作目录就回到记录的 cwd；环境变量缺失只补已批准的非秘密变量；依赖/服务不在本环境时停止并写 NOT_RUN 或 PARTIAL；测试失败时进入 Phase 9 界定影响，只有确认是本任务问题才修复并重验受影响命令。宿主拒绝、用户授权范围以外和疑似破坏性副作用都不能靠换工具规避。

最终记录包含命令来源、授权/范围、真实输入与输出、退出/停止状态、日志位置、证据 ID、未覆盖路径和恢复结果。示例命令只能在作者明确标为“示意、不可执行”时出现；正式学习步骤必须先填入已核实的目标项目命令。

作者把实际跟做步骤写在学习者已经打开的项目页面旁边，并沿用 [学习者 AI 协作卡](learner-ai-collaboration-card.md) 与 [Phase 7 playbook](phase7-beginner-lab-playbook.md) 的提示/人工复核方法。保留记录作为审计附件；正文只解释本次输入、观察和限制，不要求学习者重复创建一套通用追踪表。

## 5. 把观测写成项目专属学习步骤

在教程里先说明本次业务动作和成功时学习者能看到的结果，再进入运行操作。命令出现前解释依赖、runner、输入、环境和工作目录，说明每个实际参数如何影响本次检查。

给读者一个具体界面路径：打开目标仓库的哪个目录/文件，切到哪一个终端面板，确认终端显示的 cwd，再粘贴哪条已核对命令。标注命令读取或创建的实际文件；只观察屏幕输出时说明本步不新增项目文件。

提示框内容必须带齐目标源码范围、输入、命令、授权范围、期望观察与停止条件。AI 先回述计划和可能影响；读者核对之后才在已有授权内执行。读者对照真实输出检查一项关键值，并用文中正常/失败推演解释结果。

失败时教材带读者回到实际报错和 runtime record 的对应字段：先区分路径、配置、依赖、服务和业务断言，再按已授权范围选最小恢复动作。无法安全恢复时保留 NOT_RUN/PARTIAL 或失败，不让 AI 用自信语气替代实际证据。
