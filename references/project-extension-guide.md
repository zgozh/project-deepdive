# 项目扩展练习指南

这是一种由自然语言提示驱动的写作与学习协作方式：AI 根据本指南读取当前可用的项目索引、知识图、证据、源码和测试配置，和作者或学习者完成一项有界扩展练习。它不代表另有自动扩展引擎或专用命令。

练习围绕学习者已经学过的一条真实业务工作流展开。目标是看懂项目现在怎样工作，再沿着项目已经存在的扩展接缝完成一个小而可核验的改动。扩展点可以是注册表、插件接口、工厂、路由、事件处理器、配置、持久化接口或项目中确实存在的其他入口；不能预设项目采用某种 Agent 架构、语言或框架。

## 选择真实的扩展接缝

先从已学章节、工作流图和知识图中挑一个学习者能复述的功能，再选一个能通过仓库证据确认的扩展点。初学者不需要先读整套语言教材，但首次出现的名词、缩写、框架职责和命令都要先用白话解释。

定位时查看已存在的注册点、接口实现、创建与调用关系、路由或配置入口，以及对应测试。结合当前知识图、调用图、源码和证据卡，从接缝沿调用方向追到真正处理业务的位置；需要时追到调用者和输出使用者。只凭文件名、类名、注解名或常见框架习惯不能证明注册、调用或运行时行为。

先讲清接缝当前负责什么、由谁创建或注册、谁读取它、具体值如何进入和离开、哪些测试覆盖它。若源码证据或调用关系缺失，明确写为 UNKNOWN 或待定位，并补做有界的源码检索；不能用虚构路径、符号、调用链或架构填空。

如果项目找不到 Agent 注册表，就寻找证据支持的同类扩展入口。若当前材料不足以确认任何合适接缝，暂停练习设计并列出缺少的文件、符号或测试证据；不得为了完成练习而编造接口。

## 从业务请求形成最小改动

用一句具体业务情景说明谁需要什么、当前行为和期望结果。将任务限制在一个可以沿已有接缝完成、并能通过实际测试或其他明确检查核验的增量。

先讲本练习需要的先修概念和已有功能，再说明它在架构中的位置。对存在前端的项目，贯通用户操作、界面状态、API 客户端、后端、持久化和界面更新；对没有某一层的项目，标出实际边界。

作者应根据源事实列出受影响的真实文件、符号和相邻接口，并解释每项与变更的关系。分清已有文件、计划新增文件和受保护文件。说明输入输出、分支、状态变化、调用交接、兼容影响和相关风险；无需罗列与本次需求无关的企业议题。

把验收条件写成可观察结果，例如给定具体输入时返回什么、哪些已有行为继续成立、错误如何返回或被上游处理、哪项测试或检查能验证变化。拒绝条件、空值、异常、重试、权限、并发或性能只在真实设计触及时纳入。

## 按阶段带学习者完成

这些阶段用来组织真实的人机协作；它们由作者或学习者逐步完成，不表示运行了一个自动状态机。若练习包含源码修改，沿用 [Phase 7 VibeCoding 合同](phase7-vibecoding-contract.md)中的作者交付职责和十一阶段方法；面向初学者的讲解可参考[练习编写手册](phase7-beginner-lab-playbook.md)。

1. **BASELINE**：记录真实仓库根目录、当前 revision、工作区状态、已学工作流、可用环境和获准的读写范围。指出如何保护原有改动；不要假设有 Git、分支或特定工具。
2. **DISCOVER**：从证据找出现有能力、扩展接缝、调用路径、关联测试和未知点。用业务情景演示当前正常路径；选一条真实失败路径，说明失败会在哪一层被处理。
3. **SPEC**：写明用户需求、参与者、输入输出、范围内外、可观察验收条件和当前未知。说明为什么所选接缝适合这项改动，并列出受影响接口与兼容风险。
4. **PLAN**：画出当前及预期调用链，标出真实文件和符号；比较必要的实现选择；列出一个或多个有序小切片及相应检查。每个选择都说明取舍和证据，不虚构架构决策。
5. **SLICE**：挑选第一个可独立完成的最小切片，确认允许修改和新增的确切路径、受保护范围、完成条件及需要的测试。
6. **BUILD**：只有用户明确要求实现且授权范围具体时，才让 AI 在该范围内编辑。展示修改前后的真实差异，逐项解释新增或改变的职责；仅讨论设计或训练时不写目标代码。
7. **VERIFY**：先查看真实项目的测试配置、已有命令和运行前提，再选能覆盖此切片的最窄命令或检查。记录确切工作目录、命令和原始结果；没有执行的项目写 NOT_RUN，并说明原因。
8. **REVIEW**：逐项审查实际 diff、受影响调用方、错误路径、数据和兼容性，以及测试是否覆盖验收条件。由独立审阅者或单独的复核步骤依据源码和 diff 查找问题；AI 的自我肯定不是证据。
9. **REPAIR**：对确认的问题做最小修复。修复改变了什么行为，就重跑直接受影响的检查并记录真实输出；没有新证据时不要重复运行未变化的失败命令。
10. **FULL-CHAIN**：从同一个具体输入重放关键值的转换、分支、返回、异步续接、错误处理和下一步。项目含前后端时核对前端到后端再回界面的链路；未运行的部分标明静态推演或未知。
11. **RETRO**：总结用户可见行为、实际改动和核验结果，记录未覆盖范围、尚存风险和未知。计划、写入、测试、审查、部署及回滚等状态分别以真实证据说明。

## 作者交付给初学者的完整材料

最终练习正文必须已经填入本项目的真实材料，不能把空模板、占位路径或等待作者填写的提示交给学习者。至少交付：

- 与学习结果相符的业务情景、必要先修解释、当前行为、扩展点及其证据定位。
- 真实路径和符号、完整且必要的源码内容、行号、上游输入和下游输出；不要截断一个决定性分支或返回。
- 覆盖每个展示源码块全部行号的专属解释表，并说明关键变量、条件、调用、副作用、返回或异常的去向。逐行覆盖不是语义验收。
- 同一具体输入的正常与失败路径推演，包括关键状态变化、异步交接和真实错误处理；未知行为照实保留。
- 学习者可直接发送的完整提示词，清楚说明目标、背景材料、授权范围、所需输出和核验步骤。
- 每一步真实工作目录、涉及文件及用途、实际修改内容、需要运行的命令或其他检查，以及如何观察结果。只允许的路径和命令必须来自本项目证据。
- 完整的一次示范修订或答案：包括真实或明确标作模拟的提案、人的核对理由、追问、完整修改结果和接下来的判断；不得只列评分标准。
- 复盘所需的真实差异、检查结果、剩余未知和继续条件。未运行的命令标为 NOT_RUN；静态验证、人工推理和运行结果分别表述。

对展示的每个核心源码范围，继续使用[源码主题写作卡](phase6-source-topic-writing-card.md)的完整作者覆盖职责。它承接旧教材的17项教学职责，不要求拆成17章或17份文件。它还要求源码前讲情景、先修、架构位置和输入输出，源码中解释关键行的职责，源码后演算因果和用法。不要在扩展练习里重造第二套章节目录。

语言和框架的底层知识按当前仓库实际栈选择。先用初学者能懂的术语解释，再结合可定位源码说明项目如何使用；通用机制可以引用官方资料或明确标为通用解释，不能伪装成项目运行事实，也不能默认 Java 注解、Python 装饰器或其他语言机制通用。

## 检查与完成条件

命令从当前项目的配置、锁定依赖、测试和已有文档中确认，选实际可运行的最小检查。作者应把真实 cwd 和命令填入教材；不要在示例中把未经核验的命令当成通用默认。不得把 mock 结果写成真实端到端行为。

若需检查 Project DeepDive 已注册的 JSON artifact，可从 Skill 根目录查看现有 `scripts/validate_artifact.py --help` 并传入一个实际存在的文件。此检查只说明已注册 schema 结构有效，不证明项目事实、调用链、代码运行或教学质量。没有相应 artifact 时不要制造一个来宣称已验证。

完成练习前确认：扩展点在真实项目中有证据；当前架构、变更文件/符号、受影响调用链、测试和风险都已说明；完整需求到结果的因果链可复述；实际验证与 NOT_RUN 项区分清楚。这样才满足 AC-15、R-032 和 G16 对真实扩展点、影响分析与测试的要求。

如果关键接缝、调用路径、用户授权或验证前提仍未确认，练习保持待补证或部分完成，并指出具体缺口。格式检查、引用链接和 artifact schema 检查都不能代替真实来源核对、实现审查或完整教学验收。
