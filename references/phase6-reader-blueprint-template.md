Use a few steps as a theme-splitting starting point, not a limit on teaching depth. Classify each key source as **main teaching**, **in-place support**, **navigation only**, or **deferred deep dive**. For a key architecture or business behavior taught in this theme, show the necessary source excerpt here and explain its responsibility, input, processing, output, and next hop; a path and line range only helps the learner verify, it does not teach. A whole-project overview may lead with a diagram and a few key excerpts without dumping the implementation.

For each source excerpt, identify the pinned snapshot and byte range. Retain exact source bytes and render any teaching annotations as a deterministic overlay; do not retype code to make it look cleaner. Put required concepts and mechanisms before the project code that depends on them. Explain the needed framework and lower-level mechanism, including each component's role, input/output, failure path, and resource boundary. The minimum no-framework equivalent must demonstrate the mechanism it claims; do not merely rename a call or use a dictionary/callback that omits the key operation. If a core outcome remains unlearned, name its exact follow-on lesson and do not count it as achieved. These are author-planning requirements; current tools do not mechanically verify teaching depth.
