# 使用案例：从项目地图到可跟做的 AI 开发练习

本页是 Skill 包内的完整使用指南。普通对话会表达自然语言目的；`learn-project` 等名字是路由标签，不是命令、斜杠入口或插件名。凡是 `<尖括号占位项>` 都要先替换成你真实的路径、需求或经核对的项目材料。

先区分两个界面：**AI 对话界面**用来读项目、提问、查看方案和 diff；**终端**只在你决定执行真实项目命令时使用。本文代码围栏中的 shell 命令是终端命令，正文中的可复制提示是发给 AI 的消息。若 AI 无法读取目标目录，就让它说明缺少什么，提供对应文件或改用可读取的工作区；不要让它猜项目文件。

下面的回复内容是演示格式，不是本地项目运行记录。路径、分支、命令输出和测试状态都必须从你的真实仓库取得。

## 先认识操作用语

| 词语 | 含义 | 阅读或操作时要留意 |
|---|---|---|
| 仓库 / 宿主 | 仓库是项目文件所在的位置；宿主是提供 AI 对话和 Skill 读取能力的应用。 | 先确认 AI 当前读到的仓库根目录，以及宿主是否能访问它。 |
| revision / 工作区 | revision 是一个已命名的代码版本；工作区是磁盘上当前打开的文件，可能含尚未提交的修改。 | 说明本次依据哪一版、是否含未提交改动；无法确认就写 UNKNOWN。 |
| cwd | 终端当前工作目录。相对路径和命令通常从这里开始解释。 | 每条终端命令都给出真实 cwd，避免在错误目录操作。 |
| diff | 文件在修改前后的差异，通常标出删除和新增的行。 | 查看完整实际 diff，确认没有越过批准范围。 |
| 源码符号 / 调用链 | 符号是函数、类、方法等代码实体的名字；调用链是它们在一次功能处理中如何依次传递输入和结果。 | 每一跳都要有实际源码或运行证据，不能只凭名字推断。 |
| 测试 seam（测试接缝） | 程序中可以在测试时替换依赖或控制输入的位置。 | 有 seam 只表示便于隔离检查，不表示相关测试已运行或覆盖完整行为。 |
| vertical slice（纵向小切片） | 一次完成一个有意义行为的小增量，跨过该功能实际需要的层。 | 按业务结果划分，并列出真实文件与能核对的完成条件。 |
| UNKNOWN / PARTIAL / NOT_RUN | 分别表示证据不足、只完成部分范围、尚未执行。 | 保留真实状态；不要把未知或未运行自动说成通过。 |
| mock / 静态推演 | mock 用替身模拟依赖；静态推演按源码推演可能路径，不运行程序。 | 两者都不证明真实数据库、服务或用户界面运行结果。 |

下文首次出现这些词时可回看本表。任何术语如果仍影响本轮判断，先用当前项目的具体例子解释，再继续操作。

## 案例一：第一次学习一个真实项目，并写出第一章

这个案例从确认项目目录开始，先建立地图，再进入一个业务主题。它不默认生成整本教材或沿用旧的 17 节批次。

### 第一步：给出目标仓库和学习资料目录

在 AI 对话中发送。把两个路径改成你自己的绝对路径；如果希望只在对话里学习、不写文件，也要明确说出来。

```text
请用 Project DeepDive 从零带我理解这个真实项目。

目标仓库根目录：<替换为项目的绝对路径>
学习资料目录：<替换为我选择的目录；不要默认写回源代码仓库>

先确认你实际能读取这个仓库，并查看真实目录、README、必要配置和入口文件。说明你看到的当前 revision 或工作区状态；若无法确认就写 UNKNOWN，并告诉我需要提供什么。不要假设文件存在，不要运行目标项目、安装依赖或修改源码。

第一轮请先完成项目导读和学习路线，不要直接生成整本教材。按这个顺序说明：
1. 这个项目解决什么问题；当前能从 README、文档或源码证实什么。
2. 从一个真实用户任务开始，画出业务流程和系统整体地图；把已证实的边界与未知分开。
3. 解释理解后续主题需要的工程基础和先修概念；只补这个项目实际需要的概念。
4. 找出一条证据充足、范围适中的真实功能路径，给出正常路径和一条有意义的失败路径，以及你读到的文件和符号。
5. 建议下一章的主题和学习资料目录中的输出位置，说明理由，等我选择后再写正文。

默认读者只有基础编程意识。解释术语后再使用；不要按仓库目录顺序或固定批次数组织课程。发现前端时，路线应尽可能连接界面、状态、API 客户端、服务端、存储和界面更新。不要把静态关系说成运行时已发生。
```

### AI 第一轮应给什么

先给可核对的项目画像、来源路径、符号、revision/工作区边界和未知项。再给业务地图、必要先修、候选主题、正常/失败路径及建议路线。候选章节名应由项目真实业务确定，不能从示例复制成项目事实。若找不到能贯通的链路，应列出缺失证据并缩小目标，不得补造调用关系。

### 人先核对，再决定下一轮

- 打开 AI 列出的路径，确认文件和符号确实存在，场景与项目文档或代码相符；文件名相似不足以证明业务关系。
- 检查状态说明是否区分了已提交 revision、未提交改动和未知。若 AI 没读到完整的关键函数或错误分支，先要求补读，再选择主题。
- 确认路线先介绍必要概念，再讲业务和架构，之后才依赖那些概念的代码。
- 指定一个主题、读者范围、允许读取的源码和学习输出路径。地图通过不代表全仓覆盖或整本教材通过。

### 第二步：要求写一个有界主题

在同一 AI 对话继续发送；如果要开新对话，把第一轮已核实的主题、revision/工作区状态、路径、源码材料和未知项一起附上。

```text
根据刚刚核对过的项目地图，我选择主题：<填写实际主题>。

目标源码版本或工作区：<填写刚才确认的实际 revision / 工作区状态>
本章输出到：<学习资料目录中的实际中文语义路径>
本次范围：<填写要讲的业务功能和允许读取的路径>

先复述本章要回答的业务问题和不会覆盖的范围，再读取确切源码。面向初学者写成完整的一章：先解释直觉、先修概念、项目中的业务场景和架构位置，再展示一条完整功能闭环；把实际源码放在同一章对应解释处，按职责解释每个选中源码范围，并用同一输入回放变量变化、分支、返回、调用交接、异步续接与错误处理。包含正常路径和一条真实失败路径；提供完整练习题和推理完整的答案。

源码代码块保留实际代码，不用省略号删掉决定性逻辑；每个文件的代码块之后紧跟该文件专属的行号职责表，覆盖展示范围内每一行。重要项目事实旁标真实相对路径、符号或行号。运行事实只引用真实运行记录；仅静态分析得到的候选明确标成候选，没读到的行为写 UNKNOWN。

正文放在我指定的学习资料目录。若需要保留索引、来源快照、审核记录或结构化产物，把它们放在与读者正文分开的内部资料目录；先告诉我路径规划，不要把机器 ID、JSON、原始日志或作者状态混进章节。不要创建固定总章数或默认 17 个标题。
```

### 第三步：审阅整章和答案

人先完整阅读装配后的整章、每个练习和完整答案，再让 AI 对照真实源码查事实。可发下面的复核提示，并把实际稿件、源码或可读路径附在同一对话里：

```text
请复核这份完整章节和全部答案。你必须实际读取章节全文、每个练习的完整答案，以及支撑它们的源码；如果有内容不可读，请停在对应结论并列出缺口。

请选章节中的一个代表性输入，复演正常路径和有意义的失败路径：关键值怎样变化、走了哪些分支、在哪里返回或交接、错误怎样处理、最终观察到什么。核对先修是否早于首次使用，源码解释是否含场景/输入、代码职责、因果变化与下一步，答案是否与正文的推理一致。

逐项报告：实际读取的稿件路径与版本；源码证据；已复核内容；未覆盖内容；学习缺口；未知行为。若被评审的章节字节可确定，请记录对确切装配文件计算出的 SHA-256。不要因链接、行号、hash、脚本退出码或摘要齐全而宣称教学 PASS。发现核心缺口时列出完整受影响小节及修订建议，并保持待审状态。
```

章节实质修改后重新审阅受影响内容；最终接受前仍须重新通读和演算整章。示例中没有真实 SHA-256、退出码或测试结果，因此不会伪称已经生成。

### 第四步：保存进度并继续

将路线、已完成主题、已核对来源和未解决问题保存到你选定的资料目录。源文件变化后先核对影响范围，再沿用仍有效的证据。下一次恢复时在 AI 对话里附上进度文件和当前仓库状态，发送：

```text
请从我提供的学习进度和当前仓库状态恢复。先确认目标目录、revision / 工作区变化、最后完成的章节和待办；核对变化会不会使旧来源或结论失效。保留仍有效的材料，只继续最早一个未完成主题。列出本轮要读取的实际路径和输出位置，发现状态不足就询问缺失资料，不要依赖聊天记忆或声称后台已继续。
```

## 案例二：把一次 VibeCoding 练习做成可跟做的多轮课程

VibeCoding 是从需求到复盘的人机开发过程，不是复制一条 prompt 就结束。完整学习链是 `BASELINE → DISCOVER → SPEC → PLAN → SLICE → BUILD → VERIFY → REVIEW → REPAIR → FULL-CHAIN → RETRO`。这些阶段可以在一章或几章中组织，不表示工具替人自动执行。

### 先让作者根据真实项目准备实验

这是给 Skill / 教材作者的提示，不是学生的实现请求。填好路径后发给 AI；若指定练习需求在仓库中没有证据支持，作者应先澄清需求或报告缺口，不得编造现存文件。

```text
请基于我当前可读取的真实项目，为零经验学习者编写一份可跟做的 Project DeepDive VibeCoding 教材。

目标仓库：<真实绝对路径>
读者稿输出目录：<我选择的目录>
任务意向：<真实业务需求；如果尚未决定，让你先从源码证据中建议一个有界扩展点，但不要自行实现>
基线：<实际 revision / 工作区状态；不知道就先检查并报告>
读写与命令许可：<明确允许的读路径、可写路径、可执行检查；没有授权的动作不要执行>

先读取实际项目和已有教材，选一个边界清楚、能从现有源码核对的增量。把现有功能、计划新增内容、受保护文件和未知分开。前端项目要从用户操作连到状态、API 客户端、服务端、存储和界面回写；仓库没有某一层时标明真实边界。

教材必须逐一教完 BASELINE、DISCOVER、SPEC、PLAN、SLICE、BUILD、VERIFY、REVIEW、REPAIR、FULL-CHAIN、RETRO。每个有意义步骤都写明：
- 学生当前在哪个界面（AI 对话、终端或编辑器），终端 cwd、当前分支/隔离状态；
- 实际读取、创建、修改或保护的每个真实文件路径，以及用途；
- 学生可直接复制的完整 AI 提示词和它应附带的项目材料；
- 明确标记为模拟的示例回复；说明真实模型回复可以不同；
- 人如何依据源码、业务验收和真实命令结果核验；
- 核验通过时如何进入下一步，失败或资料不足时可复制的下一轮提示和恢复条件。

正常开发中的每条实际命令都必须来自该项目的配置或已有文档，并交代 cwd、参数、观察结果和失败恢复。区分方案、计划、实际编辑、检查、独立复核和人工接受；没执行的命令标 NOT_RUN。不得伪称已经运行、部署或发布。

每个核心源码片段须嵌在相应章节，给真实路径、范围、专属逐行职责解释表和源码前中后的业务/值回放。练习题和完整答案同篇。读者文件用中文语义名称；内部 JSON、IDs、provenance、原始日志和审阅记录留在单独资料目录。

先交代证据版本、选题与边界，再给整份教材和答案。不要空模板，不要只列评分清单，不要把静态编译状态说成实施、验证或教学验收结果。
```

### 教材中的每轮操作都要有具体交接

学生通过 AI 对话和真实终端推进。下表中的尖括号必须由作者依据目标仓库填成真实路径、命令、输入和预期；它们是填充位，不是声称文件已经存在。每轮提案都要等学生与证据核对后再决定下一步。

### 1. BASELINE：知道从哪里开始

**界面 / cwd / 文件：** AI 对话中提供仓库根、当前 revision、`git status` 实际结果（若有 Git）、环境与许可；终端只在被允许时查看这些信息。记录原工作区保护边界，不先改文件。

**学生复制给 AI 的完整提示：**

```text
我正在学习 <实际项目和任务>。现在只做 BASELINE，不编辑文件、不运行目标代码。

仓库根是 <实际路径>；我提供的 revision / 工作区信息是 <实际输出或 UNKNOWN>。请读取 <已确认可读的项目说明与配置路径>，说明你实际看到了什么、哪些前置条件可用、哪些未知。复述本轮允许读写的路径、允许命令和受保护范围。不得把旧检查结果当成这次运行结果。

交付：基线摘要、真实证据路径、环境缺口、当前授权边界，以及继续 DISCOVER 的具体条件。
```

**模拟回复 / 人的核验：** 模拟内容应填实际输出，例如“revision `<实际值>`；工作区状态 `<clean / 有改动及其路径 / UNKNOWN>`”。学生核对路径与命令原文；没有证据就保留 UNKNOWN。

**下一轮分支：** 基线和许可无误才进入 DISCOVER。路径、revision 或授权不清时，先发追问要求读取真实状态；如果有未保存改动，先保护它，不覆盖工作区。

### 2. DISCOVER：找到现有功能和改动接缝

**界面 / cwd / 文件：** AI 对话提供真实需求意向。作者列出本轮 AI 实际读取的入口、调用方、被调用方、错误处理和相关测试；终端 cwd 是仓库根或实际工具要求的位置。

**学生复制给 AI 的完整提示：**

```text
继续对同一条任务做 DISCOVER。只读取基线许可内的实际源码和相关测试：<由作者填入已确认存在的文件路径与范围>。

用业务语言说明当前行为和目标位置。追踪输入经过的真实函数、分支、状态变化、返回/异常和下一跳；区分源码直接显示的行为与尚未证实的运行时接线。指出最小扩展点、相邻调用方和可复用测试 seam；不要修改文件。

用表格列出每条结论对应的实际路径、符号/行号和证据。资料不够时列出下一份需要读取的文件，不要猜接口。
```

**模拟回复 / 人的核验：** 作者给出一条已由源码核实的调用链示例；学生打开路径确认方法和分支，检查测试与实现是否真的相连。测试名称本身不能证明执行过。

**下一轮分支：** 找到接缝并能说清当前行为，继续 SPEC。缺少调用一跳就补读那个具体实现或调用点；候选关系未解析时继续标未知。

### 3. SPEC：把需求写成可以判定的结果

**界面 / cwd / 文件：** 在 AI 对话中提交业务目的和 DISCOVER 已核实的现有行为。本轮先不写代码；如项目已有需求文档，标明实际读取路径。

**学生复制给 AI 的完整提示：**

```text
依据我刚才核对的现有行为，为这次 <实际业务需求> 写 SPEC 草案。

明确使用者、当前行为、期望输入/输出、正常结果、空值或失败条件（仅纳入这项设计真正涉及的边界）、范围内外和可观察验收条件。每项都要指回真实业务材料或源码依据；新增假设单独标注为待我决定。不要写实现方案或修改文件。

把验收条件写成我能用具体输入观察的句子，并列出仍需澄清的问题。
```

**模拟回复 / 人的核验：** 模拟例子使用实际需求输入的占位说明：`给定 <真实输入>，系统应返回/显示 <可观察结果>`。学生核对结果符合使用者目的；约束和边界必须由项目证据或用户决定。

**下一轮分支：** 每项行为都能判断满足与否，进入 PLAN。验收含糊或扩展了原需求，就追问并把 SPEC 改回已确认的最小范围。

### 4. PLAN：比较方案并作出有证据的决定

**界面 / cwd / 文件：** AI 对话；本轮通常只读。若仓库已有架构决策或 API 约定，列出真实文档路径。唯一决定来源写入用户批准的任务计划文件；没有要求保存时不要擅自创建。

**学生复制给 AI 的完整提示：**

```text
针对已确认的 SPEC 和 DISCOVER 证据提出最小实现方案。请比较复用现有接口与其他必要选项，说明兼容性、状态/数据影响、错误处理和维护代价；只分析本需求涉及的方面。

每个方案都列出真实路径、符号、调用方与证据，不猜项目约定。推荐方案并说明理由、尚未定案的问题和可以先做的有界探针。不要编辑代码，也不要把建议说成已经批准的决定。
```

**模拟回复 / 人的核验：** 回复使用“选项 A/B、证据、影响、代价、待定项”结构。学生比较它与已有接口/配置；发现引用路径不存在时要求纠正，不能据 AI 自信程度通过。

**下一轮分支：** 人批准一个方案并记录理由，才进 SLICE。选择依据不足时读取所缺的真实文件或做获准的小探针；不要开多个并行实现来回避决定。

### 5. SLICE：将批准方案分成可闭环的小步

**界面 / cwd / 文件：** AI 对话中明确每个切片要读写的真实相对路径、受保护文件和将使用的检查。尚未开始编辑。

**学生复制给 AI 的完整提示：**

```text
把我批准的方案拆成最小的有序 vertical slices。每个切片说明业务变化、修改/新增/保护的确切路径、依赖顺序、可观察完成条件和可验证的检查。检查名与命令必须来自本项目已读配置/文档；若还没找到真实命令，请写 UNKNOWN 并说明如何查找。

本轮只输出计划，不写文件。指出第一个可以独立闭环的切片；等我核对路径、范围和检查后再开始 BUILD。
```

**模拟回复 / 人的核验：** 模拟清单只填真实确认过的文件；计划 CREATE 的新文件明确标“计划新增”，不可列成当前已有文件。学生检查切片是否有输入、行为和可观察结果。

**下一轮分支：** 每个切片范围明确、先后关系可解释且首个切片可独立核验时，批准首个 BUILD。若路径或检查来源不明，回 DISCOVER 补证；若过大，继续拆分。

### 6. BUILD：只实现一个已批准的切片

**界面 / cwd / 文件：** 在工具可读写的 AI 对话/编辑器中操作；仓库 cwd、分支/隔离目录和已获准写入路径由本任务真实信息填入。学生审阅 diff，避免把计划文件当成代码已写入。

**学生复制给 AI 的完整提示：**

```text
请实现已批准的第一个切片：<已批准的验收条件>。

目标仓库 cwd：<实际工作目录>
允许改动：<逐条列真实的已授权文件路径>
保护范围：<逐条列出或写无>
不得运行的命令/动作：<真实限制>

先复述要改的文件和行为，再做这个切片的最小修改。保留范围外内容，完成后报告真实变更文件并给出完整 diff。不要提交、推送、部署，也不要扩大到下一切片。
```

**模拟回复 / 人的核验：** 示范 diff 应标为模拟，并引用作者从实际项目填入的代码。学生在编辑器读实际文件和完整 diff，核对行为、授权范围、原有未提交修改是否保留。没有真正写入工作区的文本提案不算 BUILD 完成。

**下一轮分支：** 变更仅在批准文件内且符合 SPEC，记录当前 diff 并进入 VERIFY。发现越界或丢失原改动就停止后续动作，恢复基线并报告，不在意外状态上继续。

### 7. VERIFY：依据真实配置运行最窄检查

**界面 / cwd / 文件：** 先读仓库真实测试配置、README 或开发脚本。只有需要执行时才打开终端；作者须写明精确 cwd、命令、参数及观察什么。若未获准执行则保持 NOT_RUN。

**学生复制给 AI 的完整提示：**

```text
我已经检查实际 diff。请根据本项目 <真实配置/开发说明的路径> 选择覆盖当前切片的最窄检查。先给完整命令、cwd、每个专用参数含义和预期观察项；不要虚构脚本名或假设依赖已安装。

我会执行获准的命令并把原始 stdout/stderr 摘要和退出码贴回。你再解释它实际证明了什么、没覆盖什么。没有执行的命令明确写 NOT_RUN；失败先保留原现场，不要把失败结果改写成通过。
```

**终端操作 / 模拟回复 / 人的核验：** 终端先确认 cwd，再执行作者从项目文档确认的命令。教材中的模拟输出必须标 `示例，非本项目实测`。学生保留实际退出码、测试收集数、通过/跳过数和失败摘要；退出码为零也不能把被跳过的目标行为说成已验证。

**下一轮分支：** 检查覆盖 SPEC 且结果符合预期，进入 REVIEW。失败保留原结果并带着相关 diff 与输出到 REPAIR；缺依赖时不擅自安装，先报告环境缺口。

### 8. REVIEW：独立看需求、源码和完整实际 diff

**界面 / cwd / 文件：** 第二个复核步骤或独立审阅者使用 AI 对话；提供原 SPEC、完整实际 diff、被影响源码、测试/命令真实结果。不要只给实现者的自述。

**学生复制给 AI 的完整提示：**

```text
请独立审查原 SPEC、实际源码和完整 diff，并对照这次真实 VERIFY 结果。逐项检查业务验收、调用方、正常/失败分支、错误处理、数据/API兼容和范围外改动中与本功能相关的项。

每个发现给出文件路径、行号或具体 diff 依据、影响和可复现条件。区分确认缺陷、待核实疑点和无依据的误报。不要替我改文件，也不要仅因为实现者说通过就认可。

结尾列出阻塞项、可继续项和建议的最小下一步；对未覆盖范围保持明确。
```

**模拟回复 / 人的核验：** 示例审查意见必须对应真实代码位置；作者要同时给出一项被证据否决的模拟误报，让学生练习复核。学生打开对应源和 diff，确认是不是实质问题。

**下一轮分支：** 确认的问题进入 REPAIR；经源码反驳的误报记录依据后继续。没有阻塞缺陷时进入 FULL-CHAIN。意见冲突时补看争议证据，不按多数票决定。

### 9. REPAIR：围绕一个确认问题最小修复

**界面 / cwd / 文件：** AI 对话或获准编辑器，工作区基于当前实际 diff；本轮只允许影响该问题的文件。

**学生复制给 AI 的完整提示：**

```text
复核确认的问题是：<复制一条带源码证据的实际问题>。请只提出并实施能修复此问题的最小修改，不变更原 SPEC，不处理未确认的推测。

先解释 before → after 和涉及路径，完成修改后给完整新 diff。指出本次改动使哪些先前检查失效，以及必须重跑的最小受影响检查。不要重复运行没有被改动影响的检查。
```

**模拟回复 / 人的核验：** 人对照 before/after 确认修复只改变预期分支，检查是否引入范围外变化；模拟结果不可替代真实重新执行。

**下一轮分支：** 修复范围正确，按其影响重跑直接相关的 VERIFY，然后回 REVIEW 核对修复。需求漂移或新设计决策退回 PLAN；没有缺陷时不制造一次 REPAIR。

### 10. FULL-CHAIN：用同一输入重放真实跨层路径

**界面 / cwd / 文件：** 依据实际 UI/API/服务/数据层源码和已获准的运行观察；逐层列出现存路径。没有某层就写不存在或未接通，不把 mock 代替真实后端。

**学生复制给 AI 的完整提示：**

```text
用 SPEC 中同一个具体输入，从用户可见入口开始重放本次改动后的完整功能路径：界面事件 → 状态/API 客户端 → 后端处理 → 持久化或明确的无存储边界 → 返回与界面更新；同步说明失败路径的回程。

每一步给真实文件/符号和输入值、分支、状态变化、返回/异常与下一跳。标出哪些来自源码静态推演，哪些是我实际执行观察到的，哪些仍 UNKNOWN。不要把局部单元测试、mock 或构建通过说成全链路运行通过。
```

**模拟回复 / 人的核验：** 课程作者用同一输入给出逐层值表；学生照真实源码核对条件、值和 handoff。若这次没有执行端到端操作，结论标为“静态推演，未运行”。

**下一轮分支：** 每一层都能解释且缺口已标出，进入 RETRO。某层找不到调用依据就补证，不能根据前端请求候选假定后端 endpoint 或数据库效果。

### 11. RETRO：留下真实结论和下一步

**界面 / cwd / 文件：** 回到 AI 对话，总结 SPEC、实际 diff、真实检查结果、独立审查及完整链覆盖范围。只写到用户选择的学习目录或明确批准的任务记录。

**学生复制给 AI 的完整提示：**

```text
请根据本轮真实 SPEC、完整 diff、VERIFY 原始结果、REVIEW 和 FULL-CHAIN 记录整理 RETRO。

分开记录：用户可见行为；实际改了什么；真实通过、失败或未运行的检查；审查确认和排除的问题；静态推演与实际运行的边界；未覆盖范围和未知；学到的机制与下一项有依据的练习。计划、写入、验证、审查、部署和人工接受分别标状态。不要创建我未指定的目录/文件，不宣称已经部署或发布。
```

**模拟回复 / 人的核验：** 人确认每项完成状态有对应文件、命令结果或审查材料；“下一步建议”仍是建议，不会自动变成批准计划。

**下一轮分支：** 在实际任务记录中保存恢复点后结束，或由人明确选择另一切片并重新核对计划、工作区和许可。不要在后台自动继续。

## 其它常见请求：可复制提示、输出和判断标准

下面提示适合窄任务。依然要先替换仓库路径和要解决的问题；若宿主能读取当前工作目录，也要先确认它确实对应目标仓库。

### 盘点仓库 `project-scan`

```text
请盘点 <目标仓库路径> 的 Git 跟踪文件与分类覆盖。先确认快照和工作区状态，复用仍有效的输入；如需重新扫描，使用 Skill 文档中实际存在的 scanner，报告输入、输出路径、状态、UNKNOWN/PARTIAL 项及跳过原因。不要执行目标代码或安装目标依赖。
```

预期输出是文件覆盖范围和未知项报告；不要把分类完成说成源码讲解或测试通过。需要判断结果时，核对实际 CLI 退出码、`coverage.json` 中的计数和限制原因。只有明确要求全部分类时，才请求严格无未知项。

### 看系统地图 `project-map`

```text
根据 <已确认可读的项目文档、来源证据和相关源码路径>，整理系统职责、业务闭环、组件边界与必要先修。只用已验证来源和适用的实际工具结果；区分候选、推理和 UNKNOWN，指出仍需补的调用关系。不要默认生成教材。
```

预期输出含业务流程、源代码支持的组件关系、先修概念和证据缺口。确认每条跨组件边都能回到源码/文档；不能追到的边标待验证。

### 窄文件或机制学习 `project-study`

```text
请只讲解 <真实相对路径/方法/机制>，范围限制为 <具体问题>。先说明它解决的用户问题和必需概念，再读取调用方、完整相关实现、错误分支和需要的测试。用真实源码按职责解释，并以一个输入回放正常/失败值、返回与下一跳；最后给完整练习答案。未知路径先核实，不从文件名推测。不要扫描全仓或生成整本书。
```

预期输出是一个可独立理解的解释、源码定位、因果回放和完整答案。检查所选范围是否完整覆盖关键分支；此请求不等于全仓覆盖。

### 项目面试 `project-interview`

```text
请围绕 <目标项目和真实主题> 做初学者可理解的项目面试练习。先列出问题依赖的实际项目证据，再一次问我一个问题；根据我的回答追问或纠正。示范答案区分源码事实、实际运行观察和推断，指出证据缺口；不要编造目标行为。
```

预期输出是有项目依据的问题、逐轮追问和具体反馈。若问题无法回到实际源码或项目材料，先删改问题，不把通用知识伪装为项目事实。

### 方案或扩展 `project-extend`

```text
基于 <真实业务目标>，先读取 <已知相关路径> 并找出现有行为、可扩展接缝、调用方、错误路径和测试 seam。比较最小可行方案、影响文件、兼容风险和验收条件，指出未知并给一条有界实现切片。当前只做方案；没有我的明确实现请求与写入范围授权，不修改文件或执行命令。
```

预期输出是源证据支持的方案和可检查切片；路径、接口和项目约定均须核对。提案不是实施结果。

### 质量审计 `project-audit`

```text
请按 <明确审计范围> 检查 <实际稿件/产物/证据位置>。列明确切输入与版本、执行过的检查及原始结果、没有覆盖的内容、教学缺口和 UNKNOWN。分别报告结构/来源/运行/教学证据；不得根据工具通过、hash、计数或旧记录推导未执行的 PASS。
```

预期输出是范围化结论及待办。判断发布状态时对照包内正式质量门禁和验收标准；本审计提示本身不构成接受。

### Git diff 定向更新 `project-update`

```text
请比较教材基线 <revision A 或已冻结状态> 和当前仓库 <revision B / 明确工作树状态>。先检查暂存、未暂存与未跟踪文件，按真实路径和 diff 片段列变化；追到受影响的事实、源码符号和学习章节。保留未变且仍成立的证据，仅修订受影响内容，并标明未映射项、需要的窄检查和未运行项。不要声称有自动 diff 影响映射器，不重写无关章节。
```

预期输出是可核查的影响表与局部修订方案。核对 revision A/B 的实际含义；只有路径相同不能证明旧解释仍成立。没有 Git 时改用明确冻结的文件清单和字节依据。

### 增量材料 `project-book` 和恢复续学

请求一章或一个语义主题，不要默认请求完整旧批次：

```text
请为 <项目与版本> 的 <业务主题> 撰写/更新一章。使用直接源码教学路径，读取本章需要的真实完整源码范围，在同一正文中安排解释、练习和完整答案；按证据给路径/行号，写明正常与失败回放、未知项、这次实际教学复核范围。只保存到 <用户指定路径>；没有认证生命周期输入时不要伪造 receipt 或正式发布状态。
```

恢复时提供已有章节、已保存进度、当前仓库版本/状态和上轮未完成项：

```text
请核对我提供的进度记录和当前项目状态后继续。先指出源码变化会影响哪些已学结论，复用其余仍有效证据，从最早未完成主题推进。先确认目标输出路径，不根据聊天历史猜测，不重复未受影响的检查。
```

## 限制与核验要点

- 自然语言模式名不是命令行。CLI 只按 Skill guide 与实际脚本参数调用；用工具前阅读对应 `--help`，不要从 mode 名称造出命令。
- Python 工具通常要求 Python 3.11+ 并使用标准库。Java 静态解析需要 JDK。前端解析只在明确需要时用包内锁定的 TypeScript parser；其脚本依赖按包内说明安装，不安装目标项目依赖。
- 普通源码优先的学习可以直接读取必要文件，不强制先运行 scanner、图谱编译、生命周期、构建、目标测试或部署。
- 静态候选、计划、mock、结构检查和文档编译不能证明目标代码运行、API/数据库真实接线、教学效果或发布已接受。
- 新项目教材按读者的中文语义路线组织；项目地图、必要工程基础、业务功能、同章源码/机制/失败与扩展逐步展开。没有固定总章数、每批类别数或默认 17 个标题。
- 通用 Skill 已按 AC-25 接受为 `PASS_WITH_WARNINGS`；用户新生成的教材仍须独立审查，并满足包内正式质量门禁与验收标准后才能发布。
