# 多智能体编写与独立审查（可选）

本页说明怎样把长教材任务分成可交接的小块，同时保留主会话对整体路线和最终教学质量的责任。只有当当前宿主确实支持子智能体时才采用这种分工。Project DeepDive 不要求特定模型、模型厂商、子智能体接口或并发能力；模型和宿主会影响实际可用方式与结果。

## 分工原则

“主会话”指负责和用户沟通、维护全书路线并作最终判断的会话；“作者”或“来源调查者”指受托完成明确范围的子任务。开始时先核实宿主实际提供哪些子智能体、可否并行及其调用限制；不能确认就记录 `UNKNOWN`，不要假设有特定模型、自动后台任务或可持续运行的代理。

| 角色 | 负责什么 | 不能替代什么 |
|---|---|---|
| 主会话 | 核对项目和输出位置，规划按业务与先修组织的路线，划分边界清楚的任务，整合章节，独立通读最终稿与全部练习答案，演算正常和失败路径，并决定是否接受。 | 不能用作者自评、结构检查、源码字节匹配或摘要代替完整教学审查。 |
| 章节作者 | 在明确的输入材料、先修和唯一输出路径内撰写指定章节；交付正文、练习完整答案、必要的来源记录以及实际未知项。 | 不能自行把自己的稿件标成来源接受、教学接受或已发布。 |
| 来源调查者 | 对指定功能链窄范围核对真实文件、符号、行号、分支和交接，向作者提供可复用证据及限制。 | 不能把静态源码证明成运行行为，也不能替代章内读者可见的完整源码教学。 |

一份文件同一时间只由一个作者修改。可以并行的任务必须拥有互不重叠的产物，而且彼此没有先修依赖；整本教材通常按语义路线顺序推进，因为后续章常依赖前面的概念、术语或已解释数据结构。可以提前窄取证的主题，也不等于可以跳过读者先修顺序或直接并行写依赖章节。

## 从整书请求到章节验收

主会话先根据项目事实规划路线，通常从项目全景进入业务与架构，再补实际需要的依赖、配置、应用入口和工程基础；之后按先修关系解释 DTO、实体和帮助代码，沿真实功能链讲机制与失败，最后扩展到 VibeCoding、工程判断、面试或其他用户目标。实际顺序应由项目和读者路线决定，不是固定章数或固定模板。

每个章节任务都给作者一个可执行的范围：目标读者和主题、已完成的先修材料、固定源码 revision 或未知状态、允许读取的路径、唯一正文输出路径、可复用来源记录、需要完成的练习与答案，以及本次不覆盖的内容。证据、作者材料和机器记录放在用户指定的工作记录目录；读者需要学习的源码摘录则留在正文，配有场景输入、完整必要范围、自适应的逐行职责表、代码前中后的解释和同一输入的正常/失败回放。

章节进入最终审查前，主会话实际读取装配后的完整章节和每一道练习的完整答案，并用章内的代表性输入复演正常和失败路径：值怎样传递，分支怎样选择，在哪里返回、交接或异步续接，错误怎样返回，用户最后能看到什么。先修术语要在首次使用前解释；UI、状态、HTTP 客户端、服务端和存储之间的交接必须按实际证据说明。来源工具和文档检查只证明各自范围，不能替代这次完整阅读和教学判断。

## 可复制的请求

### 启动整本教材任务

把路径换成真实位置后，可直接向主会话说：

```text
请使用 Project DeepDive，为 <项目路径> 编写面向初学者的完整教材。读者正文写到 <输出目录>/教材，进度、来源快照和内部审查记录写到 <输出目录>/工作记录。先核对实际可读取的项目版本、已有资料和宿主权限，再按业务和先修关系规划整本书：从整体认识、业务/架构、所需依赖/配置/入口，到先修组织的 DTO/实体/辅助代码，再到真实功能完整链、框架机制和工程实践，最后根据项目扩展到 VibeCoding 和面试。顺序可按项目证据调整，不要求固定章数。

开始前告诉我这次宿主实际支持哪些子智能体或模型、并发和调用限制，以及第一个任务的主题、输入、唯一输出路径和依赖；不确定就写 UNKNOWN。若支持子智能体，主会话负责路线、切片、整合和最终独立审查；作者只修改指定的不冲突文件。依赖关系明确的章节按路线顺序完成，不并行写同一文件。每章都要给完整练习答案，主会话通读最终整章和答案，检查源码解释、先修、业务上下文、完整行表和正常/失败回放。发现问题时把明确小节退回作者做一轮连贯修订，然后由主会话重新审查受影响内容和最终稿。

每个有意义的里程碑保存简短进度记录，分开写 draft、source review、teaching review 和 copied 状态，并列明已完成项、当前稿件、证据、未知、阻塞与下一项具体操作。按先修顺序继续，不要每章结束都无故等待我确认；只有缺少必需输入或权限、可用额度不足，或我明确暂停时才停并记录可恢复状态。
```

### 分配一章给作者

给子智能体的任务可以按实际需要填写：

```text
请只负责 <语义主题> 这一章，读者是刚接触该项目的初学者。

先修材料：<主会话已接受或要求先阅读的章节/概念>
源码依据：<固定 revision、已冻结快照或需窄取证的路径>
唯一正文写入路径：<输出目录中的章节文件>
内部记录路径：<用户指定的工作记录子目录>
允许读取和写入的范围：<精确目录/文件>
本章回答的问题：<业务问题与主要价值交接>
不覆盖范围：<后续章节或未证实的行为>

请写完真实场景、必要先修、业务上下文、完整功能链和失败路径。每个源码块说明其真实路径与范围，展示学习者需要理解的完整逻辑；源码前说明场景和输入，代码后紧跟覆盖展示行的职责表，并用同一输入解释值、分支、返回、交接及结果。提供完整练习和推理完整的答案，标清 UNKNOWN。请回报实际改动、路径、revision、运行过的检查及其结果，不自行宣布来源或教学通过，不修改其他章节或他人文件。
```

主会话收到稿件后应先检查它的路径和范围，再完整审阅章节与答案；不能因子智能体声称已复核就直接复制发布。来源调查与写作可以分开委派，但调查者需要交付被核对的证据和边界，作者仍需将相关材料解释给读者。

### 退回一个明确问题

如果审查发现错误，反馈应包含读者看到的问题、依据和唯一修复范围。例如：

```text
退回本章的“请求失败后的页面状态”小节和练习答案第 2 题：正文说请求失败会清空旧列表，但你给出的页面源码只有错误提示和 loading 收尾，没有清空 pageData 的分支。请只修这两个相关位置，使用已经提供的源码材料；如果仍无法证明状态会被清空，请改为 UNKNOWN 并调整答案。不要改其他章节或源码摘录。一次修完受影响解释和答案后，回报实际 diff 与新稿件身份，状态仍保持待审，等主会话重新阅读。
```

反馈只限定真实影响范围，但答案、图和其他依赖段落若也受影响，就一起在一个连贯修订中更新。若错误涉及共享事实或先修章节，先处理依赖再重新复核受影响章节。

## 无子智能体时与成本控制

若当前宿主不支持子智能体，在同一会话里按“路线与证据 → 章节写作 → 重新通读与回放”的顺序工作，或在另一个对话里提供完整稿件和证据作补充审查。后一种做法仍不保证上下文独立；不要声称已并行委派、后台仍在运行或失去会话后自动找回未保存文本。

按任务大小选择实际可用的模型和工具，不要求某个命名模型。开始前可以让主会话报告实际可用能力、当前子任务和状态；缺失能力就写 `UNKNOWN` 并采用顺序工作。为控制成本，不要把一章切成许多微任务，也不为简单编辑调用子智能体；复用仍有效的冻结来源证据，将一个相关章节缺口作为一轮连贯修订，在完成后做一次直接适用的检查。只有变更影响更宽的共享合同或发布边界时，才扩大验证范围。

跨对话续写时，把用户指定输出目录里的 checkpoint、当前章节和项目 revision/工作区状态一起提供。checkpoint 字段与恢复提示见[中断恢复与模型适配](中断恢复与模型适配.md)。这里的工作方式只是组织建议；记录不构成自动任务系统，模型切换也不保证质量相同。
