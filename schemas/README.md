# Project DeepDive artifact schemas

This directory contains the public contracts for persisted Project DeepDive intermediate artifacts.

Historical plan, verification, and acceptance titles in this file are plain provenance labels only. The shipped schemas, scripts, and packaged contracts define current behavior; an installed Skill does not require the repository's development-history files.

## Version policy

- Schema directories are grouped by major version (`v1/`, later `v2/`).
- Every artifact declares a semantic `schema_version`.
- **Registered v1 versions are not global.** All registered kinds accept `1.0.0`. `project-index`, `coverage`, `stack-profile`, `evidence`, and `static-analysis` also accept `1.1.0`, each with its own version-specific contract. `knowledge-graph` has separate 1.1.0 and 1.2.0 contracts; `evidence` has separate 1.2.0, documentation-only 1.3.0, and folded 1.4.0 contracts; `general-learning-unit` has a separate `1.1.0` contract while retaining its 1.0.0 replay contract; and `phase3-run` has an opt-in 1.1.0 package contract. Only `static-analysis` accepts 1.2.0 through 1.5.0; other registered exceptions are limited to the evidence contracts named above.
- Readers reject unknown kinds, malformed versions, unsupported major versions, and versions not named by the selected schema. Unregistered v1 minors fail closed. Schema registration alone does not imply Principal acceptance beyond the scope recorded for each slice.
- A compatible v1 minor may add optional fields only after the v1 schema and compatibility tests accept both old and new v1 artifacts. Removing or changing required fields needs a new major version and a migration path.
- Existing replicate-learning batch manifests and gate JSON remain under their existing contracts. They are not silently reinterpreted as these artifacts.

## Phase 3E2A portable run package (bounded slice accepted 2026-09-25)

## Opt-in repository documentation evidence (schema versions 1.3.0 / 1.1.0)

The explicit `scripts/repository_documentation_evidence.py` CLI accepts repeated `--selection PATH:LINE_START:LINE_END` selectors for tracked, UTF-8 Markdown files up to the Phase 3A reader's 1 MiB limit. Selectors are relative to the analysed repository root and use inclusive one-based lines. It reads the exact Phase 2 worktree or Git-tree snapshot through the shared Phase 3A snapshot reader. Evidence v1.3.0 records only a fixed generic summary, E2/`repository_documentation`, the selected locator, whole-file SHA-256, exact original-byte span SHA-256, and span byte count. For CR, LF, and CRLF files the span starts at the first selected line and includes that line's line ending when present; a final line without a newline ends at EOF. A final line ending does not create an extra selectable blank line. Raw Markdown, URLs, and credential values are never copied into the artifact or CLI summary.

The evidence states only that the selected repository documentation span records a repository declaration. It does not establish that the declaration is implemented, true at runtime, or user-confirmed. `phase3-run` v1.1.0 is emitted only when `documentation/evidence.json` is supplied to `scripts/assemble_phase3_run.py`; no-documentation packages keep the existing v1.0.0 contract and layout. Validation reconstructs every documentation evidence record from its stored selector and the same pinned snapshot, so changing a digest and recomputing package member hashes does not authenticate a false source span. Revalidation still requires the matching repository root. This opt-in evidence intake does not complete Phase 3 or change Phase 4+ consumers.

## Phase 4B claim audit contracts (1.0.0)

`claim-candidates` and `claim-evidence` each have an isolated 1.0.0 contract. The auditor checks the declared graph/evidence file paths and raw-byte digests, validates the pair, independently revalidates the original Phase 3 run/root, then compares both parsed artifacts to `reproject_phase4_graph_artifacts` output with array ordering preserved. Pair validation alone is internal coherence, not source provenance. Invalid inputs or replay mismatch fail closed without an output; a well-formed audit failure publishes the complete matrix and exits non-zero.

`SUPPORTED` means only that at least one E0–E5 evidence item and every declared reference resolves; it does not claim semantic entailment or claim-inventory completeness. Phase 4B's exact Phase 4A replay admits only E1/E2 evidence. An inserted E6 record is rejected as a provenance mismatch; a missing E6 ID stays `UNVERIFIED` and a critical such claim fails. `INFERENCE` remains reserved for a future authenticated extension and is not reachable through the 4B Phase 4A-only input contract. The 4B slice does not establish full Phase 4, R-010, or R-011 acceptance.

## Phase 6C5A opt-in Markdown v2 chapter format

The v2 chapter format is selected only by the exact comment `<!-- project-deepdive-chapter-format: v2 -->` immediately after `# Chapter`. Unmarked chapters keep the existing v1 grammar as the default. The first eight v2 sections accept one physical line per natural multi-sentence paragraph or top-level dash bullet, ending with ASCII or Chinese sentence punctuation. A single supported claim marker at the end classifies the whole line as CLAIM; without it, the whole line is GENERAL. Phase 6B1 creates one deterministic occurrence for every prose or bullet line, so unmarked project facts remain visible to the evidence reviewer.

V2 requires at least one Source excerpt. Each excerpt contains 1–20 consecutive source lines within an authenticated E1 evidence locator; its displayed range may be a subrange satisfying `line_start <= first <= last <= line_end`. The immediately preceding Source location caption gives the decoded repository-relative path and displayed range, and the exact excerpt marker carries the same path/range with a canonical percent-encoded path. The verifier reads the pinned snapshot through the existing safe path reader and checks the selected original source bytes and their SHA-256 digest. If the excerpt reaches source EOF and the final source line has no terminal LF, the LF before the closing Markdown fence is framing only and is excluded from the selected bytes and digest. V1 keeps its existing optional full-locator excerpt behavior. Arbitrary HTML, diagrams, and fenced blocks remain invalid; only the format comment and bounded SOURCE-EXCERPT block are allowed.

This is a Markdown acceptance change only. It does not add an artifact, change a schema or version, alter evidence IDs or B1 result rows, or change publication paths or the v1 default. Exercise blocks remain question-only and draft status remains unchanged.

| `project-index` | `content_kind`, `media_type`, `extension`, `vcs_object_id` | each `files[]` entry |
| `coverage` | `classification_policy_version` | top level |
| `coverage` | `secondary_surfaces`, `rule_id` | each `entries[]` entry |
| `static-analysis` | `roles[]` and `CALL_CANDIDATE`, `EXTENDS`, `ROUTE_TO` relation kinds | top level / `relations[]` |

Payload semantics for the new fields:

- `content_kind` is one of `text`, `binary`, `symlink`, `gitlink`.
- `media_type` is derived from a versioned internal table plus a bounded byte sniff — never from the host MIME registry, so two machines classify the same tree identically.
- `extension` is the lowercase final suffix without the dot, or `""` when the name has none.
- `vcs_object_id` is the Git object ID from `git ls-files --stage` (worktree snapshot) or `git ls-tree -r` (git-tree snapshot).
- For a symlink, `bytes` and `sha256` describe the link-target payload. For a gitlink (submodule entry), they describe the ASCII Git object ID and `media_type` is `application/x-gitlink`; the nested repository is never traversed.
- `secondary_surfaces` lists other applicable surfaces, sorted and deduplicated, and never repeats the primary `surface`.
- `rule_id` is a stable built-in rule ID, or `override:exact-path` for a human exact-path override.

`reason` stays the human-readable explanation. Required reasons, sorted secondary surfaces and version-specific invariants are enforced by the semantic coverage audit (`scripts/coverage_audit.py`), not by JSON Schema conditionals.

## Paths, snapshots, and incomplete coverage

- `project.root` is the analysis root. File paths and evidence locator paths are relative to it and must not escape it.
- `project.snapshot_kind = "git-tree"` means file byte counts and SHA-256 values describe blobs from `repository_revision`; `"worktree"` means they describe bytes read from the analyzed checkout.
- `coverage` may temporarily contain `classification = "UNKNOWN"` while analysis is incomplete. G01 can pass only after `unknown_count` is zero and every entry has one of the five final classifications.

## Slice 3A stack detection

Phase 3A consumes an audited Phase 2 `project-index` and `coverage` pair and emits compatible schema version `1.1.0` for `stack-profile` and `evidence`. Both outputs carry identical `source_metadata`: `snapshot_kind`, G01 `PASS`/`PARTIAL`, `unknown_files`, and lowercase SHA-256 digests for the two Phase 2 inputs. Each digest is computed over the UTF-8 bytes of `dumps_artifact(input)`, which sorts object keys and writes normalized JSON with a final newline; array order remains part of the input. V1.0.0 fixtures remain valid and loadable without this field.

Schema validation checks metadata field shape. Semantic/cross-artifact validation additionally requires it for v1.1.0, checks that the two outputs agree, enforces `PASS` iff `unknown_files` is zero (`PARTIAL` iff it is positive), and compares the metadata to the audited Phase 2 input pair. A later consumer that checks the recorded digests must load the corresponding Phase 2 inputs. Every positive detection's evidence IDs must resolve to E1/E2 declaration evidence. A `VERIFIED` stack entry means its declaration was found in a supported manifest; it is not runtime evidence or proof that a dependency is installed or used.

Dynamic TOML keys in evidence locators use `[key-sha256:<64 lowercase hex>]` segments rather than echoing the key text. To verify such a locator, enumerate keys at the indicated parent in the original snapshot and compare their UTF-8 SHA-256 values. Dotted and quoted TOML keys remain distinguishable through this deterministic locator rule.
