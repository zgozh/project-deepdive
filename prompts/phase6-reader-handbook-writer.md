# Phase 6 读者手册编写提示

请依据操作员提供且已冻结的 Phase 6 材料，编写一份初学者可以实际阅读和学习的中文手册。遵守[读者手册契约](../references/phase6-reader-handbook-contract.md)。读者手册是面向人的教学作品，和机器可审计的 canonical 章节稿是两种不同产物。不得把 canonical `chapter.md` 直接复制、改名或拼接后作为读者稿；需按读者路线实际编辑正文，并单独复核其教学深度。canonical 语法检查通过、sidecar 状态为 `REVIEWED_DRAFT`，或旧版本曾经通过审查，都不能证明这份新手册已达到教学质量。

## 书级路线与读者成品

目标项目、源码快照/证据版本、教材范围与交付目录以操作员提供的书级计划为准。手册从项目整体目的、用户业务和架构开篇，再进入当前授权范围内有证据支持的功能；curriculum unit 只是证据输入，不是一篇读者章节。每个项目都依据自己的书级计划确定版本、路径和范围。

整体地图之后，按目标项目实际采用的技术栈，核对后续主题需要的构建与依赖、配置、程序入口与装配、执行环境等基础；在功能深读依赖某项基础前，先讲清必要机制。只讲项目实际使用的文件与框架，不预设语言或框架。初始章节与覆盖边界由书级计划结合冻结工程材料确定，不预设固定章数或路径终点。不得把已讲的局部流程误写成完整端到端覆盖，也不得由有限初始集推断工程基础或全项目覆盖已经完成。

读者教材根目录由书级计划指定，不使用跨项目固定路径。书级计划可用少量清晰有语义的篇目分组（如工程基础、业务功能、机制与工程验证），也可在顺序中文 Markdown 文件名前加篇名；不得为每个 curriculum unit 建杂乱目录，也不要求一单元一章。旧的平铺顺序文件继续兼容，不强制迁移旧预览或覆盖旧文件。目录 `00` 导读说明读序、本次材料覆盖和仍待覆盖范围，不充当源码教学。练习和完整推理答案放在同一章正文，紧跟练习；小例子及关键输入/结果写在正文，长示范作为纯 Markdown 附录。源码缓存、脚本、review、provenance、manifest、检查报告和其他开发附件留在仓库 artifacts，不放入读者根目录。已有读者预览保留作历史记录，不能被当作当前正式教材。

## 输入与证据边界

只使用本次明确提供的 canonical 产物、已接受的审查结果、冻结源码快照和补充证据。操作员应提供输入版本和源码 revision。对于 `git-tree` 快照，只能通过获准的只读 Git object reader，在指定 revision 读取材料引用的源码字节；不能用当前 worktree 代替。未经明确授权，不得执行目标代码、写入目标仓库或造成外部副作用；已授权的官方资料查询及冻结 Git 对象只读读取可用于小范围补证，无需重复确认。


项目事实必须有冻结证据支持，并保持证据所支持的准确范围。文件名、类名、依赖声明、注释、提议的图边或方法名，单独都不能证明职责、运行时装配、实际执行、持久化、消息送达或用户可见结果。用自然语言区分静态源码观察、已验证的运行时观察、通用原理和作者解释。重要事实缺少支持时，请求针对该范围验证补充证据，或清楚说明未知；不要自行补齐链路。

`CLAIM`、`EVID` 等机器 ID、哈希、packet/state 标识、schema 字段、canonical 标记、解析器指令和机器脚注语法不得出现在面向读者的正文里，应由操作员记入单独的 provenance 记录。正文可使用读者能理解的源码名称、路径、行号范围和链接，帮助读者找到依据。保留读者会在代码中遇到的标识符原拼写，并用中文解释。

## 组织学习路线

每个学习单元按[学习者 AI 协作卡](../references/learner-ai-collaboration-card.md)安排与当前学习结果直接相关的实质协作：提供具体材料和完整初轮提示，展示明确标为模拟的提案、人的逐项核验、可复制追问、完整修订与继续/恢复标准。实质操作写清起始位置、读取范围、谁写/不写什么文件及内容；复用本章已有源码、练习和答案，只补缺口。不能只让 AI 解释一次或写“请审查”；不把完整开发流程复制到每章。此要求补充旧17职责、源码前中后和完整专属行表，不替代它们；是否教会仍需独立语义审查。

默认读者是真正的初学者。按主题和业务目标组织课程：项目目的与总览、用户问题与业务流程、已知架构及其边界、紧贴当前功能所需的前置概念、连贯的功能源码路径，最后进入机制、失败、验证和有边界的扩展练习。首次使用术语前先用通俗语言解释。保留先整体后具体的路线；不要按类、函数、文件批次或内部工作阶段组织读者目录。

叙述使用自然中文，明确谁在什么场景下要做什么、得到什么结果；用有意义的角色和业务名称，避免 A/B/C 或索引标签给读者增加转换负担。先交代故事场景，再解释术语和分析代码；教学角色或流程须标明为假设，不强行编造人物或凑故事配额。

写正文前先填写[书级路线计划](../references/phase6-reader-book-plan-template.md)：按读者的整体到具体路线定主题，再从 curriculum units 选证据输入；内部单元不是目录，也不是一单元一章。各主题继承计划里的同一贯穿场景，并说明本主题可见的中间结果与明确延后的目标。最终篇章结构和数量由书级计划结合实际冻结材料决定；初始学习路线不是固定目录，也不代表完整项目覆盖。

在选取证据前，先写明读者学完主题应能解释、推演或判断什么。writer input 只带入 blueprint 中写明的学习结果，因此每个 source-rich 主题的 blueprint 必须先列全要教的核心文件、每个文件的完整职责/待覆盖范围，以及适用的教学职责；不能只列少量 claims 或几句结果，再把它们当作完整的逐文件教学计划。blueprint 仍定义获准主题范围，不能借写作卡加入无关目标；如果它漏了本主题实际需要讲的核心文件或职责，先在授权主题内补全 blueprint，再准备作者输入。

每个普通 source-rich 读者主题都必须在写正文前使用[源码主题写作卡](../references/phase6-source-topic-writing-card.md)。卡片以已安装旧模板的 17 项职责建立作者覆盖计划，并提供逐核心文件可填写的小节骨架；它不是第二套课程目录、canonical 稿、读者必须照抄的 17 个标题或自动语义评分。旧模板和 `new_batch.py` 等成熟工具可作为起笔与确定性覆盖检查的支架；旧批次门禁仍只约束旧批次路径。当前 Phase 6 不含独立八股/面试课程或完整 VibeCoding 训练，把⑨与完整⑫记为 `not_requested`，不宣称全 17 项通过；主题中的真实底层机制⑧仍需讲清。

每个核心源码主题都要让初学者沿着具体输入推演，而不是只看代码再读摘要：

1. 先讲业务场景、首次依赖的前置概念、明确标为假设的输入和预期结果。Java 或其他语言的必需语法要在首个依赖片段前用贴近代码的小例子解释，术语清单不能代替演算。
2. 总览可用少量源码定位职责，但不计作核心源码深读。完整功能主题要展示并解释闭环所需的完整方法或连续完整职责段及其必要依赖；核心工程基础与核心源码深读保留旧 Skill 的整类/整文件注入和逐步讲解能力。按完整符号与职责边界选源码：source-pack excerpt 只作导航，不是必须的裁剪边界；优先复用已有符号起止，必要时窄读同一冻结文件到方法、构造器或类的实际结尾，不截断于 `return`、链式调用或闭合大括号。闭环依赖的私有 helper/visitor，要在本章呈现并解释必要的完整实现；否则明确标出相应学习结果未达成。小文件整件讲，长文件按连续完整职责段拆开；未教的方法和有效配置字段仍算未覆盖，几段摘录不能冒充整件已教完。源码原文、教学注释版和简化示例分开。若源码块声明展示一个完整核心符号，从冻结的符号提取事实读取其路径和起止行，并在调用 `materialize_reader_sources` 时通过 `required_symbols` 预检范围覆盖；多个连续源码块可共同覆盖该符号。这个预检只检查行范围覆盖，不证明表格对应或解释正确；有意展示的局部旁证无需声明为完整符号。
3. 用同一输入按顺序追踪关键变量、条件、赋值/副作用、输出或返回值、异常和下一跳；对关键正常/失败回程逐层分清被调用方抛出的异常、每层真实 catch 后返回的状态、日志行为，以及上游如何检查返回值。不能从 callee 抛异常推断 HTTP、CLI 或 MQ 外层一定失败。
4. 解释实际参与的框架机制、关键组件职责、最小非框架等价及其设计取舍、失败与资源边界。通用语言/框架机制可用官方资料和明确标注的教学示例充分讲解，不因缺少项目运行证据而省略必要先修或只重述 API 名；项目内部链仍受证据段约束。
5. 走一条有证据的失败路径，并给出相应验证和展示推理的完整答案。

每个核心文件或连续职责段动笔时，复制并填写下面的小节骨架；最终可以合并成更适合读者的标题：

- 业务问题；本段输入和输出：
- 首次使用前要懂的概念/语法：
- 创建者、调用时机、生命周期，以及有证据的实际调用处/调用方：
- 一个具体输入下的最小教学用法：如何交入、处理、输出或失败；简单声明不虚构调用：
- source-plan 槽位：真实路径、行号、语言、逐段解释计划：
- 每个源码块后的专属表：首列按 caption 完整覆盖仓库行号范围，其余列按职责定制：
- 源码前的业务/架构位置、先修概念、输入输出，以及源码中的变量/分支/赋值/调用/副作用/返回或异常因果：
- 同一输入的正常路径与一条失败路径：
- 真实上游/调用点如何交入输入，下游如何使用结果或检查失败：
- 机制适用时的L2关键操作教学等价及生产遗漏，L3替代方案、成本、失败面和资源边界：
- 有源码证实的扩展点及接入步骤；没有则说明范围内未确认：

对配置文件解释本主题涉及的所有有效字段。源码槽使用 `reader_source_blocks.py` 支持的整行槽位；helper 自动附带唯一定位 caption，不能再手写重复 caption，源码字节保持原样并遵守语言安全注释规则。

定义、前置概念和假设输入必须出现在首次依赖它们的解释之前；迁移段落后按最终顺序再核对。静态源码能确定的控制流和赋值直接讲清；只把缺证据的运行时行为或外部效果标为未知，不在每个调用后重复免责声明。项目实际创建、调用、状态和外部效果只按源码/运行证据支持的范围陈述；静态规则可推出的结论写明条件和推导并标为推论，不能称为实测，缺证据的项目事实保持未知且不补造内部链。已接受的 claim/evidence 是可复用证据，不是教学上限；确有机制缺口时在授权范围内窄补证据，无需重扫整个仓库。未证实的连接保持未知；免责声明不能代替教学。篇幅、标题、引用、哈希和格式检查各自只证明本身的检查范围；仍要复核学习顺序、因果推演和答案一致性。

输入、冻结源码与来源元数据已准备好时，先写完整连贯的 lesson、练习和答案，并随文维护同一份 source-plan。正文稳定后，再集中用 `reader_source_blocks.py` 呈现源码槽并收集 helper 返回的源码/片段摘要与 provenance；依据同一份 source-plan 一次整理严格格式的 `sources.json` 和旁路 provenance。helper 提供源码字节与定位信息，不替作者判断来源含义或教学质量；清单 shape validator 也不认证来源。不要手填猜测 hash 或为未变源码反复重取证据；最终正文与审查报告的摘要由既有 reader lifecycle 在相应边界绑定。

练习题应能独立读懂，并附展示推理过程的完整答案。问题应能根据本课内容和所给证据作答，不得依赖未解释术语、隐藏元数据或未说明的运行时假设。

## 正文版式与源码定位

用 H2/H3 按学习顺序组织课程。首次定义关键概念，以及关键判断或结论时，适量加粗；不要整段、整行加粗。代码符号、方法名和类名使用行内代码，并保留源码拼写。围栏内的真实源码保持原字节，不翻译、不改写，也不加粗。

正文不要出现 `[来源N]`、`EVID`、Phase/attempt 状态或机器引用占位符；使用读者看到的中文章名和学习路线，不写内部审计流程作为正文导航。把重要项目事实的真实仓库相对路径和行号放在它附近；已从源码确认且对定位有帮助时，可附方法名或类名，不能猜测。使用源码片段前，呈现为 `> **源码位置**：` 后跟完整相对路径和具体行号范围。同一小节首次引用或代码片段前写出完整长路径；后续可用文件名、已介绍且确认存在的方法名和具体行号，减少重复。引用靠近它支持的解释或推演步骤；章首大索引和末尾编号索引不能代替就地定位。哈希、证据 ID 及其他机器标识只写入旁路 provenance。

对每一个展示的项目源码块（包括总览短块），按[写作卡的源码块前、中、后规则与完整行号表示例](../references/phase6-source-topic-writing-card.md#每个项目源码块的前中后讲解与完整行号表)写块前场景/先修/输入输出、块中职责因果、块后覆盖完整 caption 行号范围的专属表和同输入推演，并说明有证据的调用方、使用方式与实际下一跳。相邻块可以共用已讲过的背景和整章回放，但每个块都须就地说明自己的输入、作用和交接；不能用“见前文”替代。机制相关时补最小教学等价、生产遗漏、方案取舍与失败面；简单声明不硬造调用或方案。

源码注释只作线索；表格按有意义职责段解释实际字段/变量变化、guard、副作用和返回/异常去向，不机械拼注释或逐行重复整块结论。表格不能代替源码前场景、先修、架构与输入输出，也不能代替源码后同输入的正常/失败推演、真实上下游用法及必要的 L1 机制、L2 关键操作与生产遗漏、L3 取舍/成本/失败面。

从不可变冻结输入和独立作者部件重建每版输出，勿在旧渲染稿上追加；行号以确定性编号的原始冻结源码核对，保留正确的既有细节并只补缺口。数字覆盖不证明行义解释对应正确。

默认命令只检查绑定到 `lesson.md` 的源码块；如果清单含 `answers.md` 块，报告会显示排除数并保持 `INCOMPLETE`。对已将练习答案嵌入或追加到 `lesson.md` 的最终整章，使用 `--assembled-chapter` 同时检查两类块：`python scripts/reader_source_explanation_coverage.py --assembled-chapter --lesson <assembled-lesson.md> --sources <sources.json> --output <report.json>`。`COVERED` 只表示该模式覆盖范围内的数字行号表完整，绝不表示语义教学或来源认证通过。

教学示例也要逐段解释，用“示例行”或演算步骤定位；示例行号不是仓库行号，也不属于 source manifest 的项目源码覆盖。

对每个关键来源标出正文主讲、就地支持、纯导航或延后深读。凡本章依赖源码讲一个关键架构/业务行为，都要在本章给出必要片段并解释职责、输入、处理、输出和下一跳；只有路径和行号的纯导航不能算已经教会。全景可以先图、再讲少量关键片段，不把全项目实现堆进总览；延后项需链接到准确后续教材章节并保留未达成的学习结果。

上述顺序和写作卡都用于规划作者覆盖与教学先后，不规定读者正文必须使用哪些标题。`1–3` 个学习结果或 few steps 只是主题切分建议；canonical 的固定结构与读者稿分开，读者稿不设固定标题数或字数要求。最小非框架等价必须实际演示所声称的机制，说明参与组件的职责、输入与输出、失败路径和资源边界；不能只改名调用，或用省略关键处理的字典/回调示例代替。必要概念和机制应先于依赖它们的项目源码。核心目标若未教会，写明具体后续课程且不得算本主题已完成。读者章生命周期会绑定最终正文、输入和报告的精确字节，但工具不会判断语义教学是否成功。

关键缩写首次出现时给出中文名、英文全称和通俗解释；图要配合逐阶段说明，并提供 Mermaid 不可渲染时仍可理解的文本说明。手写示例明确标为可运行或不可运行；只有实际包含该机制的关键操作，才能称为该框架机制的手写等价。

## 单独记录与独立复核

不要把审计 ID 或生产元数据附在读者正文后面。操作员应在单独的 provenance 记录中说明 canonical 输入版本与源码快照、复用的证据绑定、补充证据及其支持范围、新增且需要独立复核的解释/示例/答案，以及仍待完成的语义复核和书级覆盖检查。最终读者深度审查记录必须绑定经审查的完整成稿精确 SHA-256。正文修改后要对新字节建立新绑定；可复用仍适用的未变来源证明和审查结论，并独立检查改动部分及受影响的解释、因果推演、练习和答案。实质改写或改变学习路线/核心推理时，扩大语义复核到受影响的完整章节或更大范围；最终章节验收仍须按契约完整阅读组装稿和所有答案。不能用旧摘要、旧审查记录或旧 receipt 发布修改后的字节。canonical review 只复用未变事实的证据，不替代读者深度审查；已实现的读者章生命周期会绑定最终正文和报告字节，但不会自动判断教学质量。

首次章级验收要完整通读实际组装章和全部答案。对已完整通读的基线稿做有界修复时，只能为精确差异证明未变的正文/答案复用既有完整阅读证据；独立检查本次 diff 及受影响的源码职责、因果链、练习和答案。每个最终字节版本都要新建精确 SHA-256 绑定和报告，并记录基线 SHA、当前 SHA 与实际增量复核范围；不得把增量复核称为对当前稿的全新完整通读，也不得用样本宣称完整覆盖。

绑定或发布前，先把读者将看到的完整章组装好，包括最终中文标题、顺序、链接、正文源码片段和章内答案。Principal 再独立通读实际成品，并用章内输入推演关键变量、分支、输出/交接、机制取舍、失败验证和答案推理。按书级计划在开篇、架构、完整功能稿及组装稿等有意义的里程碑复核，不机械地给每章增加两轮暂停；任何影响成品字节的改动都需重审受影响内容并更新绑定。未改变的源码与证据继续复用。只检查标题、术语、篇幅或引用数量不算通过；记录实际复核范围，不能用样本冒充全项目覆盖。

`sources.json` 必须使用契约中给出的严格 `reader-theme-sources` v1.0 格式：字段名 `artifact_kind`、非空 `supports` 字符串数组、`lesson.md`/`answers.md` 槽位目标，以及对象数组形式的 `unknowns`。预写清单可调用契约里的纯 shape validator；这只检查结构和提供的 revision 字符串是否相等，不会认证、读取或证明源码，也不代表教学通过。正式 review-input 仍需 live authenticated context，并在同一验证器通过后对已绑定快照实际校验来源。每项 `critical` 必须对应本次获准的必需学习结果；未实测不自动构成关键阻断，真正缺少必需源码或因果解释仍须阻断。不得为绕既有 formal gate 擅自降级；若未授权运行目标被误列为本章必需目标，保留原记录并报告范围冲突，待 Principal 独立确认获准目标后再修正分类。

除非操作员明确要求其他产物，否则只返回指定的读者正文。正式证据绑定、独立复核和发布检查完成前，手册仍是草稿。读者章生命周期已实现精确字节绑定和受限发布，但不会自动写作或判断教学质量；现有 canonical 解析器和门禁保持不变。

## 通用读者稿的 staging 呈现

当前确定性呈现工具只支持 `general-lesson` 与 `general-answer`；`canonical-v2` 尚未实现。示例调用如下，输出和审计 JSON 都必须放在内部 staging 路径：

```text
python skills/project-deepdive/scripts/reader_handbook_export.py --kind general-lesson --input <lesson.md> --output <internal-staging/lesson.md> --audit <internal-staging/lesson.audit.json> --title "中文课程标题" --revision <source-revision-or-unknown>
python skills/project-deepdive/scripts/reader_handbook_export.py --kind general-answer --input <answer.md> --output <internal-staging/answer.md> --audit <internal-staging/answer.audit.json> --title "中文答案标题" --revision <source-revision-or-unknown>
```

工具只呈现固定标题和标签，不编写或认证教学内容；围栏代码保持原样，已知源草稿状态标记仅移入审计 metadata，输入文件不变，审计教学深度为 `NOT_REVIEWED`。结果留在 staging，Principal 按上文的逐段输入推演标准复核后，负责发布的 worker 再写正式输出；这是工作分工，不是用户 approval 系统。概念或课程单元不要求一对一拆成章节。
